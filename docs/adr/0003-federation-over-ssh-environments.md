# ADR 0003 — 用联邦取代 SSH 环境

## 状态

已接受（2026-10-18）。实现待做，见 `docs/changes/federation-design.md`。

## 背景

需要在一台机器上管理多台机器上的开发环境。已经实现并验证过的是 SSH 方案：
本地进程启动一个子 dsh，该子进程的 `fs` / `subprocess` / `sandbox` 三项服务
被 `dsh-ssh` 替换，文件与命令操作经 SSH 落到远端。

这套东西能跑通：远程环境里创建的会话能读到只在远端存在的文件。但它有三个
无法消除的缺陷。

## 三个缺陷

**① 每次工具调用 +511 ms。** `dsh-ssh` 硬编码 `-o ControlPersist=no`，
每次调用重新握手。实测中位数 511 ms，一个 20 次调用的会话多花 10 秒。

**② 宿主上产生幻影目录。** 建会话时 `dsh-api-session-controller` 执行
`mkdir(cwd, {recursive:true})`，用的是 `node:fs`（宿主）。cwd 是远端路径时，
这个 `mkdir` 在宿主也建出同名空目录。实测：`/root/remote-workspace/proof.txt`
在本机存在，在 6.13 上不存在。

**③ 远程目录无法成为工作区。** 工作区注册在 `dsh-workspace` 里用 `node:fs` 的
`realpath`，在宿主执行。远端路径必然 ENOENT，注册直接以 `workspace/invalid-path`
失败。因此「看到远端的工作区」在上游语义下无解。

## 决定

放弃 SSH 环境，改用**联邦**：每台机器跑自己的完整 dsh，主节点通过反向隧道访问它们。

同时消除三个缺陷：

- 工具在本机执行 → 无网络延迟
- `mkdir` 的是真实存在的路径 → 无幻影
- 工作区就是本机工作区 → 无 ENOENT

## 后果

**正面**：无延迟、无幻影、可访问任意远端目录、边端独立可用（主节点挂了也能干活）。

**负面**：数据不集中。会话与工作区属于各自机器，主节点看不到边端的会话列表。
这是设计选择：会话属于运行它的那台机器。

**负面**：每台边端要装完整 dsh（约 566 MB 核心 + 插件），不能像 helper 那样只放一个
73 MB 的可执行文件。对「只想借一台小机器跑个命令」的场景，联邦是过度方案——
但那个场景本身也不该用环境来表达。

## 实施约束

现有生产环境（6.13）依赖 SSH 模式工作。因此实施顺序必须是**先建联邦、验证通过、
再删 SSH 代码**，不能先删。

## 被否决的替代方案

- **修 SSH 方案的三个缺陷**：①需要改上游 `dsh-ssh`（`ControlPersist`）；②③需要改
  上游 `dsh-api-session-controller` 与 `dsh-workspace` 从 `node:fs` 改用 `ctx.fs`。
  三处都是上游包，改了会锁死版本，每次升级重打。
- **混合**：SSH 用于轻量机器，联邦用于完整机器。两套代码、两套测试、两套配置语义，
  维护成本高于收益。
- **只做并置不做融合**（每个边端开独立浏览器标签）：解决了访问但没解决「一个入口」。
