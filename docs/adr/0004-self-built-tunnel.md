# ADR 0004 — 自建隧道，不用现成方案

## 状态

已接受（2026-10-18）。

## 背景

联邦需要一个「边端主动连主节点、主节点反向访问边端」的通道。目标是边端不需要
在防火墙上开放任何入站端口。

评估了四类现成方案。

## 评估

**localtunnel / cloudflared / ngrok**

拓扑正确（客户端外连，外部经服务端访问回客户端），但检查了 `localtunnel@2.0.2`
的实现后确认三处不可用：

- 只做 HTTP 的 TCP 管道，不支持 WebSocket upgrade。dsh 的全部 API 走一条
  `/api/remote.mux` WebSocket，这条路直接废掉。
- 按子域名分配（`xxx.loca.lt`），不是路径前缀。而路径前缀（`/<envId>/`）我方已经
  实现并在生产上运行。
- 服务端（`localtunnel-server@0.1.0`）是独立应用，要额外开一个端口，与现有的
  认证、路由分离。

**frp / rathole**

是完整程序（独立二进制 + 配置文件），不是可嵌入的库。引入它们等于在 Node 进程之外
再管一个服务。何况联邦需要的路由逻辑还在主进程里，包括前缀处理、Host 改写和认证。

**socket.io / ws**

只提供帧传输，多路复用和请求-响应配对要自己写，取消传播也一样。这不是缺点——正因为
要自己写，才控制得了语义。

**HTTP/2 或 gRPC 的 stream 复用**

协议本身解决了多路复用，但引入的重量（HTTP/2 server push 语义、gRPC 的 IDL 与代码生成）
远超需要。而且它同样不解决「按路径前缀路由到不同环境」这件事。

## 决定

用 `ws` 加自建帧协议（格式见 `federation-design.md` 第 4 节），实际新增约 150 行。

## 理由

自建的成本比看上去低，因为**最难的部分已经完成并跑在生产上**：

```
routeProfile(url, ids)          前缀剥离      已有
headers.host = authority        Host 改写     已有
server.on('upgrade', ...)       WS 转发       已有
```

真正的改动是：把「目标 = 本机回环端口」泛化为「目标 = 本机端口 或 隧道连接」。
已有的前缀、Host 改写、WS 转发逻辑原样复用。

## 后果

**正面**：完全控制语义；无额外进程；复用已验证的路由代码；帧格式简单到可以
用一句话说清。

**负面**：多路复用、背压和取消传播都要自己保证正确。这些是真实风险，需要专门测试：
并发请求不串号；浏览器断开时取消传播；大响应体保持分片顺序。

## 被否决的替代方案

- **localtunnel**：不支持 WebSocket，这一条即不可用。
- **frp/rathole**：额外进程，且不接管路径路由。
- **直接绑 0.0.0.0 让主节点连入**：边端必须开入站端口，与目标矛盾。
- **只支持 HTTP 不支持 WS**：dsh 的界面完全依赖一条 WebSocket，不可行。
