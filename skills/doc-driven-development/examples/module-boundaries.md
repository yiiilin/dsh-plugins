## 摘要

本模块封装一次提交的生命周期，供入口调用。当前内容是候选 fixture 的行为描述，未经业务采纳；仅在单进程、同步发布和内存存储范围内成立。

## 1. 需求与模块约束

### 任务生命周期与重复提交
<!-- ddd:item C-IMPORT-TASKS-001 -->

有效提交生成任务并发布一次。同一请求标识和相同文本行再次提交时返回原任务，不再次发布；相同标识配不同内容时拒绝，原任务不变。
非法输入不创建任务、不调用发布函数。发布函数抛错时任务变为 failed；同标识重试返回该失败，不自动再次发布。
任务状态仅由本模块修改；调用方拿到副本，不能通过修改返回值改变内部状态。

发布依赖必须同步完成，或者在任何写入前抛错。本模块不提供真实数据库事务、崩溃恢复或跨进程去重；部分写入和异步发布超出本例约束，不能推断它们已得到保证。

### 验收条件

1. 两条有效行经正式入口提交，得到 published、行数 2，发布函数收到这两条行。
2. 相同请求再次提交，结果相同，发布次数仍为 1；内容变化则报 REQUEST_CONFLICT。
3. 空行或带空位的稀疏行数组等非法输入报 INVALID_ROWS，查询不到该任务，发布次数不变。
4. 发布函数在写入前抛错，结果为 failed/PUBLICATION_FAILED；重复提交不增加尝试次数。
5. 修改查询或提交返回的状态副本，随后查询仍得到权威状态。

## 2. 概要设计

### 职责与依赖

src/imports/index.mjs 是唯一对外入口；私有任务实现拥有 Map、请求内容指纹和状态修改权。
入口负责装配发布函数并转交请求。模块通过传入函数调用发布能力，不依赖入口实现。
允许的源码依赖是 app -> imports/index -> imports/private/tasks；精确规则见可执行检查。

<!-- ddd:diagram flow -->
```text
[提交] --非法--> [拒绝且无任务]
[提交] --有效且已有--> [内容核对] --相同--> [原结果]
[内容核对] --不同--> [冲突且原任务不变]
[提交] --有效且新增--> [创建并发布] --结果--> [状态副本]
```
校验先于任务创建；重复请求先核对内容；仅新请求调用发布函数。失败分支由任务模块收敛为 failed。

<!-- ddd:diagram data -->
```text
[入口] --标识与文本行--> [任务模块] --行副本--> [发布函数]
[任务模块] --指纹与权威状态--> [私有Map]
[私有Map] --读取--> [任务模块] --结果副本--> [入口]
```
Map 不对外导出，发布函数也不能通过传入行数组修改请求指纹。数据仅在当前模块实例内存活，进程重启后不保留。

## 3. 详细设计

### 公开契约

通过公开入口创建模块后使用 submit 和 find；精确签名与导出以源码为准。
submit 返回状态副本；find 在标识不存在时返回 null。
INVALID_REQUEST_ID 和 INVALID_ROWS 表示输入拒绝；REQUEST_CONFLICT 表示已有标识的内容不同。发布失败返回任务结果，不向外透传存储异常细节。

<!-- ddd:diagram state -->
```text
[不存在] --有效新提交--> [processing]
[processing] --同步发布成功--> [published]
[processing] --发布抛错--> [failed]
[published] --相同请求--> [published]
[failed] --相同请求--> [failed]
```
状态转换只发生在私有实现中。终态不因重试回退；非法输入和冲突均不创建或修改任务。
发布回调内的查询可以观察 processing；本例不承诺异步并发控制。

### 实现自由

Map、指纹计算与私有函数可以替换，但须保持公开结果、写入权限和依赖约束。
异步发布、持久化、失败自动重试属于新增行为与一致性选择，需重新设计契约及对应验证。

## 2. 运行真实装配与故意错误

从 skill 目录运行：

```sh
node examples/module-boundaries.mjs --run
node --test tests/module-boundaries.mjs
```

[脚本](module-boundaries.mjs)使用标准库创建新的系统临时目录，写入三个独立 ESM 文件，然后经实际入口装配并调用；退出时检查并清理自己创建的目录。它不写入当前项目，不联网、不安装依赖、不访问数据库。

执行覆盖正常发布、发布失败、同键重复、内容冲突、非法输入及状态副本隔离。随后写入两类依赖反例：入口越过公开入口引用私有实现；私有实现反向引用入口形成循环。另一个 fixture 故意把入口接成返回 null，确认行为断言能失败，即使没有违规 import。

静态检查只识别三个 fixture 文件中单行、字面量 ESM import/re-export，包含 side-effect import。它不是 JavaScript 解析器，不分析动态 import、require、别名、注释/字符串中的伪声明或其他文件。示例规则不能直接当作全项目架构扫描器；实际项目应使用符合其语言和构建配置的分析工具，并继续核对状态写入与共享数据等语义耦合。

发布适配仅模拟“同步收集全部行”或“写入前抛错”。真实适配若先写一部分再抛错，或返回 Promise，本例的假设不成立，须设计新的事务与状态机制。

输出中的 checks 是本次示例断言结果，`formalRunner: not-run` 表示没有正式项目 runner 验收。它不会生成 Verification-Receipt、批准记录或 agent 效果评测，也不能把围栏里的规格标为 accepted/passed。

## 3. 后续三种变更：只维护变化的事实

| 场景 | 应做什么 | 完成条件 |
|---|---|---|
| 私有重构：拆分 Map 查找或指纹计算 | 保持契约正文，运行公开行为与依赖检查；文件移动时修复归属、链接和检查规则 | 同样输入、错误与重复语义成立，调用方无须读取新私有实现 |
| 业务变化：失败后同标识允许重新发布 | 先讨论失败与部分写入场景，更新唯一任务契约、状态转换和失败/重复测试；涉及新选择时记录相应提案 | 新行为已确认，调用方得到明确结果，旧契约和证据不被继续当作当前有效结果 |
| 实现违规：入口直接修改任务状态或重复发布 | 恢复所属模块的修改权与去重行为，加入能在错误实现上失败的回归 | 实现重新满足现行契约；无需为了迁就 bug 修改契约 |

公开行为、业务不变量、状态归属或依赖方向变化时，更新对应主文档。私有组织变化通常不改语义正文，但绑定输入变化仍按正式 runner 规则使旧证据待复核。发现文档与代码不一致时查明原意，选择修复实现或明确修订契约；未查清则标具体待核实点，不靠更新时间或刷新哈希消除偏差。

人和 AI 共用这份契约。项目/领域 README 保持职责摘要和链接；签名、字段以代码或 schema 为准；测试数量与日志由实际运行生成。试点成功的标准是能找到规则的唯一所有者，并准确判断一次改动需要维护哪些契约，而不是文档数或静态检查全绿。
