## 摘要

这是一份**假设方案**，用于示范人类可读的三层正文和 ASCII 图，不来自用户仓库，不是可直接运行的实现，也没有人的实际批准。

假设用户要求导入失败时不留下业务可见的部分数据。候选方案为“先校验暂存，再用事务一次发布”，同一请求标识用于查询最终结果。AI 主动提出了“提交成功但响应丢失”场景：暂时不知道结果，不能简单当作失败。以下展示该候选讨论结果如何落文档。

不包含断点续传、发布后撤销和跨数据库分布式发布。实际项目需要确认接口、数据规模、故障恢复能力和查询一致性，不能只替换名称就直接实施。

## 1. 需求说明
<!-- ddd:section requirements -->

### 1.1 使用者与范围

操作者提交一份文件，业务查询方读取完成导入的数据。需求来源为本文假设场景，不是既有获批规格；状态查询和错误信息只对有权访问该批次的调用者开放。

### R-DEMO-IMPORT-001 无部分结果

任一行非法或发布明确中止时，本批次不应产生业务可见的部分结果。全部成功后，本批次的数据整体可见；“清理尚未完成”不应改变可见性。

### R-DEMO-IMPORT-002 结果不明与重复请求

如果提交结果无法确定，调用方得到“处理中/结果待确认”及可查询的批次标识，不得被告知已经失败。同一请求标识和相同内容重发时返回已有任务，不创建第二次导入；同一标识对应不同内容时拒绝并说明冲突。

### 1.4 验收条件

首行和末行非法时，均不能读到本批次部分数据；合法文件完成时全部可见。发布提交后响应丢失，使用原标识查询应能得到最终成功，不重复写入。结果尚不可判定时不能误报失败。不同内容复用相同标识被拒绝。上述是验收计划，不是已执行结果。

## 2. 概要设计
<!-- ddd:section overview -->

### 2.1 职责与边界

入口负责认证、请求标识和参数校验；导入处理器负责解析校验与暂存；存储模块拥有任务状态及批次数据，负责事务发布；结果核对器查询权威提交事实。业务查询必须通过可见性边界，不能绕过存储模块读到未发布记录。

候选前提：任务状态、批次数据和可见性判定处于同一具备所需事务能力的存储系统。真实能力需要查证；若项目无法满足此前提，应返回讨论，而不是自行改成最终一致性。

### 2.2 端到端处理流程
<!-- ddd:diagram flow -->
```text
[提交请求] --身份及参数合法--> [查找请求标识]
                                  |
                                  +--同标识不同内容--> [拒绝冲突]
                                  |
                                  +--同标识同内容----> [返回已有任务]
                                  |
                                  +--新请求--> [创建任务并校验暂存]
                                                    |
                                                    +--失败--> [明确失败；不发布]
                                                    |
                                                    +--完成--> [事务发布]
                                                                  |
                                                                  +--已提交--> [成功]
                                                                  |
                                                                  +--已中止--> [失败]
                                                                  |
                                                                  +--结果不明--> [按原标识核对]
                                                                                      |
                                                                                      +--仍不明--> [保持处理中]
```

身份或参数不合法在入口直接拒绝，不创建批次。图中核对结果确定后返回对应成功/失败；“暂时未查到”不足以证明中止。核对不盲目重放发布写入，重试机制应与存储的提交识别能力一起讨论。

### 2.3 数据流与归属
<!-- ddd:diagram data -->
```text
[调用方] --请求标识 + 文件--> [入口/导入处理器]
[入口/导入处理器] --内容指纹 + 标准化行--> [存储模块]

[存储模块] --暂存写入--> [批次数据区]
[存储模块] --任务及发布状态--> [任务记录]

[批次数据区] --批次行数据--> [业务查询]
[任务记录] --已发布批次条件--> [业务查询]
[业务查询] --可见数据--> [业务调用方]

[任务记录] --权威状态--> [结果核对器]
[结果核对器] --批次标识 + 可确认结果--> [调用方]
```

重复名称表示同一主体。任务记录和批次数据都归存储模块；发布改变该批次的可见性条件，不要求搬运所有行。业务查询是否能以所需一致性读到状态与行，需要由具体数据库和查询实现保证，不能仅靠图上的两根箭头。

### 2.4 方案与代价

暂存后发布避免将整个文件读取过程放进一个长事务，但增加暂存空间、状态存储、查询过滤和清理机制。请求标识和内容指纹处理重复提交，但保存期限与敏感数据策略需要业务确认。本文不虚构吞吐量、超时或保存天数。

## 3. 详细设计
<!-- ddd:section detail -->

### 3.1 接口与数据契约

候选逻辑接口为 `submit(requestId, file)` 与 `getResult(requestId)`。前者返回批次标识和当前可确认结果；后者返回状态、可公开的错误信息或待确认信息。请求标识唯一性由持久化约束保证，不依赖进程内“先查再插”。相同标识的内容比较必须定义稳定指纹算法及范围；不能只比较易变文件名。

实际传输协议、文件大小和保留期没有来源，列为待确认，不将示例函数名当作已确定 API。

### 3.2 业务状态流转
<!-- ddd:diagram state -->
```text
[NEW] --开始解析--> [STAGING]
[STAGING] --校验或暂存明确失败--> [FAILED]
[STAGING] --全部输入校验和暂存完成--> [READY]
[READY] --取得发布执行权--> [PUBLISHING]
[PUBLISHING] --发布事务确认提交--> [SUCCEEDED]
[PUBLISHING] --发布事务确认中止--> [FAILED]
[PUBLISHING] --超时或提交结果未知--> [PUBLISHING]
```

对象是一个导入任务，状态归存储模块；修改状态需要合法转换和并发控制。最后的自循环表示调用者暂不能确认最终结果，不能将其覆盖写回数据库而回退已成功状态。权威提交状态必须单调，核对器查询而非凭超时推断失败。

| 转换 | 守卫条件 | 关键动作或限制 |
|---|---|---|
| STAGING 到 READY | 全部输入校验、暂存完成 | 固定本批次内容，不接受“半完成即发布” |
| READY 到 PUBLISHING | 当前状态仍为 READY，执行者取得唯一发布权 | 条件更新/等价串行化，不让两个工作进程同时发布 |
| PUBLISHING 到 SUCCEEDED | 存储事务提交事实成立 | 可见性切换与成功状态必须原子关联 |
| PUBLISHING 到 FAILED | 可以证明发布已中止，不会再晚到提交 | 不能只因为网络超时或查不到成功记录而失败 |

### C-DEMO-IMPORT-001 发布与错误不变量

暂存写入不对业务开放；发布前验证任务处于允许状态、输入已完整。事务内原子改变可见性和最终成功状态，不能先暴露数据再异步补成功记录。事务失败需要区分“已确认回滚”与“结果不明”；后一种不向调用者伪报失败。

只允许原任务的有效执行者推进状态。并发发布、进程重启后的执行权回收以及数据库错误分类依赖具体存储能力，必须在落地前补齐可执行细节和验证；未确认的恢复算法不能由 AI 默默选择。

### 3.4 清理、核对与实现自由

失败批次可按明确策略清理暂存数据；清理失败只影响资源回收，不改变可见性。核对过程需要有界频率与停止条件；超过允许的自动核对预算仍未知时，停止自动轮询并显式转交人工核对，不擅自改成失败。具体预算需要真实来源。

不影响上述接口、状态和不变量的私有函数拆分、局部命名可以自主。哈希算法、标识保留期限、存储隔离能力和故障恢复不是同一级别的命名自由。

### 3.5 待讨论问题

D-DEMO-IMPORT-001：界面是否允许返回处理中及查询入口？这是方案的业务裁决点，本文尚无实际批准。

D-DEMO-IMPORT-002：真实存储能否保证可见性切换、最终状态与读取视图一致？需要调查并验证；不能以“文档已这样写”停止查证。

D-DEMO-IMPORT-003：故障后执行权如何回收，未知提交怎样得到确定结果？需要结合真实数据库和任务执行器设计，当前仅建立了问题与约束，不授权实施未确定的恢复机制。
