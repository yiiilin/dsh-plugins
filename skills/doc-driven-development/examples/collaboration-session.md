# 假设多轮协作：确认立即记录，不把解释变成审批

本页是训练/评估示例，不是运行日志，不来自真实业务仓库；没有调用模型或记录实际批准。`FEAT-IMPORT` 等名字仅示意，不能复制为真实事实。

## 场景一：需求仍在讨论，部分边界已经确认

**使用者：** 请求超时后重试，不要创建第二个导入。但我主动重新导入同一个文件应该允许。

**AI 应做：** 先区分同一次提交与新的业务操作。用户已经明确这两个边界，不重复提问；只更新本次提案对应段落，现行规格仍保持原版本。一次真实写入的内容形态可以是：

```text
D-IMPORT-003：重试与主动重新导入
状态：已明确确认；方案记录，尚未实施。
场景：提交请求超时后带原请求标识重试。
决定：返回原任务，不新增任务。
边界：用户主动发起的新导入使用新标识，同一文件可以再次提交。
理由：避免网络重试重复处理，同时不禁止新的业务操作。
确认来源：当前用户对上述场景和边界的明确要求（实际使用时填可定位来源）。
实施授权：尚需确认任务其他关键机制；本条不能扩展为批准整个方案。
剩余：记录保留期、不同内容复用标识的处理、失败恢复。
```

**保存后回执：** “已写入本次提案的 D-IMPORT-003：同一次提交重试复用原任务，但新的导入不受限制。保留期和恢复机制仍未定。”

只读场景改为明确“还未保存到文件”，不能复用上面的保存话术。写入前发现提案已被人修改，先读新版本并做小范围合并，不用旧全文覆盖。

## 场景二：解释先于名词，只让人裁决需要裁决的部分

**不应问：** “幂等键 TTL、锁租约和重试 budget 怎么设？”

**应先说：** “第一次导入可能已经在服务器处理，只是响应没回来。重试必须找到这次任务，而不是再建一次。用固定请求标识查原任务的机制叫幂等处理。代价是要保存标识与任务的关系。你刚才已经决定了重试与主动新导入的边界，所以不需要再选一次。下一处业务问题是：结果暂时不确定时，界面能否保持处理中并允许查询？标识唯一性和存储能力我会先核对现有实现。”

用户不了解概念时，只补本场景中何时使用、处理哪个对象、如何影响行为，不整段讲理论。关键定义进入正文首次出现的位置；同一个名词在多领域含义不同须明确归属。

## 场景三：评审提出意见，主 agent 先查证而非一律接受

给只读评审者当前提案修订、D-IMPORT-003、需求来源及有关存储接口，不只给主 agent 的摘要。

**评审意见：** “同一个文件应永久禁止再次导入，否则就没有幂等性。”

**主 agent 的处理：** 对照已确认范围，此建议不成立；幂等性约束同一次请求重试，不限制用户主动的新操作。保留用户决定，不因为意见来自子 agent 就修改。

另一条意见若指出“暂时查不到任务不能证明第一次请求已中止”，需要查证实际事务和唯一约束；若成立，记录具体竞态场景与受影响流程并讨论修正。查清前不能说一定存在 BUG，也不能随意放宽需求。修复后定向复核相邻状态转换。

真实审阅后才能保存 E 评审记录。没有独立评审工具时写 single-context self-review，并说明限制；不能根据本页示例编造调用。

## 场景四：恢复任务时发现文档和代码变化

从已有提案读取已确认边界和下一步，运行 context 比较先前快照。若存储接口或依赖约束变了，回读相应文档与实现，再决定旧方案是否仍适用。不要先问用户“我们上次决定了什么”，也不能因为快照匹配就自称已读。

最新日期的 proposed 提案不是现行 accepted 规格。发现事实与已确认约束矛盾，分别记录并提出问题，不自动选一个覆盖另一个。

## 场景五：需求修订了，旧 passed 不能搬过去

需求从“相加”改成“相减”，即使文件名、R 编号和代码快照没变，规格修订/内容已经变化；旧 Spec-Refs 不再匹配。应修改已授权的实现，从新验收场景验证，再记录真实环境与对应基线。仅替换旧记录的 hash、Result 或 Approval 是虚假核对，不是修复。

设计评审通过不算实现测试通过；文档定稿也不自动授权写代码。该闭环的脚本反例在 tests/closure.mjs，脚本不能证明对话行为本身。
