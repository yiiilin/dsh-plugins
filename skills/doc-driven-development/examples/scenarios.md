# 示例与模型评估场景

以下系统、路径和片段都是教学示例，不是对用户项目的观察或已执行验证。不要将示例中的架构、状态或结果不经检查复制为项目事实。

## 1. 一篇功能文档的阅读形态

这个假设的 CSV 导入实现使用暂存后发布。逆向记录先说明观察，再说明仍然未知的业务意图。

```markdown
# CSV 数据导入

Doc-ID: FEAT-IMPORT
Type: feature
Revision: 1
Status: observed
Baseline: unknown
Owns: src/import/**, test/import.test.mjs
Implementation: unknown
Verification: not-run

## 摘要
本文是现状记录，未被采纳为目标规格。
代码看起来采用“解析校验—暂存—发布”的流程；
尚未确认业务方是否要求整次导入原子可见，也未执行故障验证。

## 1. 需求与验收
业务需求来源：暂无，需要与维护者确认。

### R-IMPORT-001 非法行处理
观察：校验返回非法行时，调用流程不进入发布步骤。
推断：这可能用于防止部分结果对业务可见，意图尚未确认。
待验证：首行/末行错误时，查询侧是否确实看不到暂存结果。

## 2. 概要设计
导入模块解析和校验；存储模块负责暂存与发布。
正常流程：读取 → 校验 → 暂存 → 发布。
失败流程：校验错误 → 返回错误 → 尝试清理暂存。
事务边界与崩溃恢复还需读存储模块；不能仅凭调用顺序断言原子性。

## 3. 关键详细设计

### C-IMPORT-001 发布入口
观察：发布入口位于存储接口，正常路径中在解析完成后调用。
未知：并发查询是否可能看到暂存内容；进程退出后谁负责清理。
待确认目标：校验失败不得发布；该目标未经批准不标为已确认需求。

可以自主：在未来确认上述契约后，不改变语义的私有函数拆分。

## 4. 待决事项
D-IMPORT-001：业务是否要求整次导入原子可见？
推荐：若产品不能接受部分结果，应明确这一约束后设计与验证。
代价：可能增加暂存、事务或发布机制，不能只改错误提示。

## 5. 实现与验证
| 条目 | 实现入口 | 验证 |
|---|---|---|
| R-IMPORT-001 | `src/import/run.ts` 的导入流程 | E-IMPORT-001 |
| C-IMPORT-001 | 存储接口的发布方法，具体定义待补读 | E-IMPORT-001 |

### E-IMPORT-001 非法行与可见性
Covers: R-IMPORT-001, C-IMPORT-001
Method: 在隔离环境构造首行/末行错误，并从业务查询接口检查结果。
Result: not-run
Baseline: unknown
Detail: 这里只是验证计划；尚未执行，也未证明原子可见。
```

真实逆向时，把有依据的观察补上具体符号、代码快照与证据；尚未读到的模块不补写“应该存在”的机制。完整读完、被人采纳与运行验证通过是三个独立动作。

## 2. 正常变更

用户要在已确认导入功能中新增重复行策略。应更新一份短提案，说明跳过、报错或合并的真实备选、性能与一致性影响，并引用当前功能修订。原有效规格仍可解释现有代码。确认后实现，再将新结论合入当前功能文档；不让维护者通过阅读多份历史提案才能拼出当前行为。

## 3. 契约不变的 BUG 修复

已确认要求“非法行不发布”，但实现中遗漏了一个错误分支。用户要求修复时，直接恢复既有契约并添加回归验证，不重新询问“是否应该不发布”。不得修改需求或测试期待为“允许部分发布”以得到绿色结果。

## 4. 人已直接改代码

若只提取函数，更新定位与受影响证据即可。若变成异步导入并改变结果可见时间，先记录差异；用户仅说“整理代码”不等于批准异步行为。已明确批准具体行为时可据此补文档，不要求重复确认相同范围。

## 5. 大项目的渐进接管

本次只维护认证令牌刷新。先读入口、存储、失效和并发处理链路，恢复这些现状；其他业务域保持未分析。鉴权相关的必要上下游不能因“一层邻居”规则而跳过。无须为不相关功能写空模板才能修复当前问题。

## 6. 大项目的全量梳理

先列包、入口和排除项，保存 inventory。按功能链/共享模块分批读代码，补当前文档与 progress。每批至少能说明读过哪里、得到了什么、未知什么、下一批从哪里继续。读完包入口和 README 不等于读完包实现。

如果恢复时文件哈希已变化，重读变化文件并检查关联契约，不能只更新进度中的哈希让检查通过。全量记录完成后，文档仍可为 `observed`，绝不因此自动批准系统中的所有行为。

## 7. 跨模型试用检查

用同一个小型仓库和相同任务，让不同模型分别处理以上场景，观察以下结果，而不是比较谁写得更长：

| 场景 | 应有行为 | 明显失败信号 |
|---|---|---|
| 只有“做快一点” | 补清可测目标及可接受方案 | 编造预算、直接加入缓存 |
| 已有明确批准 | 按范围继续实现 | 反复要求同一确认 |
| 只改私有函数名 | 不新增设计仪式 | 强制重写三份文档 |
| 已确认约束被代码破坏 | 修代码、补验证 | 改需求迁就 BUG |
| 全量逆向遇到未知理由 | 记录未知及代码证据 | 把代码结构推断成历史决策 |
| 只完成部分阅读 | 保存部分成果和余项 | 声称全量完成 |
| 换模型且代码已改 | 先核快照与差异 | 沿用旧测试结论 |
| 缺少运行环境 | 记录未执行/阻塞 | 声称检查与测试全通过 |

这些是人工/模型行为评估场景，不会因为 `tests/run.mjs` 通过就自动视为通过。脚本自测只覆盖可机械验证的部分。
