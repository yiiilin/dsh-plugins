# 共同设计、三层文档与 ASCII 图

本页规定如何思考、与人讨论以及组织设计，不替代 [REFERENCE.md](REFERENCE.md) 的确认和证据规则。**文档是讨论结论的工作界面，不是 AI 停止思考的理由。** 示例属于假设场景，不自动构成项目要求。

## 1. 共同形成方案：确认即记录，阶段性整理

```text
[用户目标 + 当前规格 + 代码事实]
                 |
                 v
[查证事实，找缺口/矛盾/隐含假设]
                 |
                 +--没有重要歧义--> [说明依据，继续已授权工作]
                 |
                 +--存在重要歧义--> [具体场景 + 后果 + 推荐及代价]
                                               |
                                               v
                                       [共同推演；每个明确决定即时保存]
                                               |
                                               +--仍有缺口--> [继续相关讨论]
                                               |
                                               v
                                       [主题收敛，整理三层设计/差异]
                                               |
                                               v
                                       [评审后核对具体批准范围]
                                               |
                                               v
                                       [实现 + 验证 + 更新文档]
```

这不是顺序不可返回的阶段门，也不强迫所有任务问答。契约清楚的修复与等价重构直接执行；发现新重要选择时只暂停相关部分。用户已有具体批准可以复用，不能把“帮我看看”“继续讨论”当作批准生产实现。

### AI 主动做什么

| 检查方向 | 需要自己调查和推演的内容 |
|---|---|
| 目标与边界 | 谁使用，何种结果算成功，不做什么，权限和外部限制是什么 |
| 场景与失败 | 正常输入、非法输入、部分成功、超时、断连、依赖失败、重复请求 |
| 生命周期 | 谁创建/改变状态，合法和非法转换，终态、重试、取消、恢复 |
| 数据 | 来源、结构变化、存储/查询、何时可见、谁负责、保留与清理 |
| 协作与约束 | 调用方/被调用方的假设是否相同，事务/并发/兼容性与预算是否矛盾 |

这是分析检查单，不是交给人的长问卷。只分析与本次工作相关的项；某项不适用需有依据。

| 问题类型 | 处理方式 |
|---|---|
| 能查清的事实 | 先读代码/配置/测试/已有规格，给来源，不请人猜代码 |
| 业务意图或代价取舍 | 具体场景、后果、真实选项、推荐理由和代价，交给使用者裁决 |
| 未知的运行性质 | 标明假设，提出最小、隔离的验证；未经授权不启动服务/联网/迁移 |
| 既定约束内的实现细节 | 自主完成，不制造无用审批 |

已确认文档存在矛盾时必须指出。允许质疑，不允许自行重写正确行为、放宽测试或声称已获批准。发现更优方案要区分“必要纠错”和“可选优化”，避免每次维护都演变成重构。

### 如何讨论

不要只问“要不要事务/重试/幂等”。例如，在一个假设的导入需求中：

> 你希望“失败不留下部分数据”。还有一个场景：数据已经提交，但成功响应丢失。此时直接报失败会诱导重复导入。建议返回可查询的处理中状态，复用同一请求标识核对结果；代价是保存请求记录与提供查询入口。我们需要确定：界面是否接受暂时不确定的结果？

一次优先聚焦同一主题最影响正确性的少数问题。给建议，不预设用户同意；不要反复询问已在当前规格或对话明确的信息。已明确接受并记录的取舍，除非出现新事实或范围变化，不反复劝改。允许先画候选 ASCII 草图，明确“候选”，不必先生成整份规格。

**记录决定、整理正文、合入现行规格是三个不同动作。** 本轮出现明确批准、撤回、否决、延期或范围变更，在本轮结束前、小范围写入已有 `changes/` 提案的“决定与继续入口”或新功能草稿；不能等全部问题讨论完，也不等用户催写。解释性对话无新项目决定时不制造写入。用户只读/只讨论优先，写入失败或无权限明确“尚未持久保存”。

记录“具体场景、决定、适用边界/例外、理由、确认来源、是否授权实施、尚未决定什么”。保留稳定 D 编号；撤回保留原结论和取代关系，不擦掉来由。含糊的“好/继续”只在紧邻、无歧义的已呈现范围内解释，不扩展授权。已有真实批准不重复请示；新增含义需确认。写前重读目标文件，若有人改过，只合并获准段落，冲突暂停，禁止整篇用缓存覆盖。

保存后一句回执给实际文件/决定编号及关键边界；未写入不能说“已记录”。不把原始聊天、敏感信息全部归档，不再建平行的聊天纪要数据库。主题收敛后将结论整理为三层正文；未确认或未实施目标不能覆盖现行规格。实现后合入当前文档，保留批准来源与证据对应，不让使用者翻历史才能知道今天的行为。完整假设交互见 [示例](examples/collaboration-session.md)。

切换主题、阶段、模型或会话前保存未决问题、下一步与已读材料基线，恢复时按 [CONTEXT.md](CONTEXT.md) 比较变化并回读；快照本身不证明已读。用户要求先给完整草案时可以采用显式假设写 proposed，不能把假设偷换为既定需求。

### 先建立理解，再请求裁决

关键概念首次出现，按自然顺序解释：**什么时候发生 → 本项目上下文/当前行为 → 希望得到的结果 → 推荐如何实现 → 代价/边界 → 真正需要人决定什么**。术语在含义之后命名；解释深度随使用者反馈调整，已有专业背景不重复教学。只解释本次决策需要的机制，不长篇上课。

例如，不先问“幂等键 TTL 和冲突策略怎么配”。先说明：“提交已在处理但响应丢失，用户重试可能多建任务；建议同一次提交使用固定标识，重试返回原任务，称为幂等处理。代价是保存对应关系。此刻请决定界面是否能展示处理中；标识生成和存储能力我先调查，保留期随后按真实业务约束确定。”

AI 负责调查可查事实、推演技术可行性并推荐；使用者主要裁决目标、可接受行为、约束和代价，不被迫在术语菜单里盲选。关键概念在正文首次出现时留一两句本项目用途/归属，反复歧义才维护小型领域术语表，不强制全局词表或排斥同义词。

### 实施前评审，不等到使用者要求开子 agent

讨论中对每个重要结论做局部冲突检查；进入实施前按风险做设计评审；修正后定向复核。普通小改可一次自审，高风险（权限、持久化、并发、跨模块协议、不可逆操作）优先使用独立只读评审者并按关注点拆分。宿主无子 agent 时单独自审并披露局限，不能虚构调用记录；必要时请求人的风险裁决，而非默默降低安全要求。

评审输入包括当前修订/指纹、原始目标、已确认决定与不做的范围、未决项和必要的实现/接口事实。评审者不只读主 agent 的结论，不改文件；主 agent 是唯一整合写入者。审阅需求遗漏、跨图状态/数据矛盾、实现可行性及跨文档假设。不要求“至少找 N 个问题”。每项意见给出位置、可复现场景或矛盾依据、影响与建议，并分类：已证实缺陷/待调查/不成立/可选改进。

主 agent 先查证，再决定采纳或给出理由；不是子 agent 一说就改。已确认取舍不因个人偏好反复重开，新事实或确证缺陷才回讨论。修复影响的相邻约束要定向复核，若修复改变重要行为/方案仍需授权。结束条件是本次已知阻塞项全部解决、范围缩小或明确接受可界定风险；其余未知可见，不追求无限零意见。

真实评审记录复用 E 条目，见 [REFERENCE.md](REFERENCE.md)，不另造审查台账。`Kind: design-review` 区分设计审阅与实现验证；记录 Reviewer（真实独立/自审）、绑定的规格与代码版本、已核实问题与处理、Open blockers。修改规格后旧评审过时，先复核再记录新版本；源码关键前提变了也须核对。脚本 `--review` 只核字段和版本，绝不生成“审查已做”的结论。真实多轮模型试点使用 [评估任务](examples/evaluation.md)，不是仅检查规则文本存在。

## 2. 三层必须分清楚

| 层次 | 回答的问题 | 不应变成 |
|---|---|---|
| 需求说明 | 谁在什么前提下需要什么结果，失败/边界行为，怎样验收 | 一句愿望，或夹带未讨论的技术方案 |
| 概要设计 | 模块责任、端到端协作、数据流与状态归属，关键取舍 | 技术栈/目录清单 |
| 详细设计 | 接口和数据契约、合法状态转换、关键处理步骤、不变量、异常与恢复 | 只有抽象原则，或逐函数复制实现 |

feature/module 保留三个一级阅读块（Markdown H2），普通功能同篇；内部小节按实际适用性裁剪。模块第一层引用上层需求，写本模块约束和验收，不复制业务规则。全局 architecture、短 change、ADR、接管报告不机械套三层。

复杂需求/详细设计已独立成文档时，在主文档对应层用摘要与明确链接导航，不要求复制全文。图可引用当前受管文档中的同类图。目录仍遵循 [LAYOUT.md](LAYOUT.md)，安装、检查不重排正文或迁移路径。

定稿的阅读顺序为：摘要（目标、总体方案、现状/候选/批准范围）→ 需求 → 概要 → 详细 → 实现与实际验证。重要要求沿用 R-/C-，证据沿用 E-，避免制造第二套编号。参考 [完整假设示例](examples/import-design.md)。

## 3. 用三种图分析不同问题

| 图 | 位置 | 节点和箭头的含义 |
|---|---|---|
| flow 处理流程 | 概要 | 节点是处理步骤，箭头标判断/结果分支 |
| data 数据流 | 概要 | 节点是参与者、处理器、存储，箭头标数据内容/变化 |
| state 状态转换 | 详细 | 节点是业务对象/任务状态，箭头标触发事件、守卫条件 |

**状态图不是文档的 observed/proposed/accepted 状态机。** 不把流程步骤、数据库记录和业务状态混为一套节点。关联对象有多个生命周期时，主图展示主要对象，子图分别说明其他对象，明确它们之间的关系。

使用 Markdown `text`（或 `ascii`）围栏，连线用 `- | + > < v ^`，节点可写中文；不要依赖渲染器才能读懂。优先短节点与纵向分支，避免全角半角混合导致宽框错位；不强求画方框边框。中文正文不限制，只有连接符使用 ASCII。

```text
[输入] --合法--> [处理] --成功--> [输出]
   |
   +--非法--> [拒绝并说明原因]
```

图后必须解释前提、分支条件、数据归属、可见性与关键副作用。简单图直接在箭头说明；复杂状态可加“原状态/事件/守卫条件/新状态/动作”转换表。算法复杂处可加伪代码，但不替代状态/数据语义。

大图按子流程分解并命名引用。正文中的接口、状态、数据名和测试场景使用相同术语。现状图只画有依据的机制；没有查清的转换明确记录调查缺口，不能把空白随便连到失败或成功。

### 沿图走查

至少选一个正常场景和一个实际相关的失败/边界场景；适用时再走重复、并发、取消或恢复路径。逐步问：读/写什么，谁改变状态，何时可见，异常由谁接手，用户看到什么，测试如何观察。

孤立状态、无主数据、无来源输入、未定义异常、跨图矛盾必须说明。发现后能自行查明的查明；需要业务决定的讨论；不为通过检查虚构重试、事务或性能保证。

## 4. 最小机器约定（不替代人读图）

新建或本次明确完成结构升级的 feature/module，在现有头部添加：

```text
Design-Format: layered-v1
```

检查器识别中文“需求说明/需求与验收/需求与模块约束、概要设计、详细设计/关键详细设计”，英文 `Requirements`、`High-level design`、`Detailed design` 等常见 H2 标题，允许数字前缀。其他语言或既有标题不必改名，在相应 H2 后紧接下列独立标记（允许空行）：

```markdown
## 项目原有的需求标题
<!-- ddd:section requirements -->

这里保留需求说明正文。
```

另两层标记为 `overview` 和 `detail`。三层各一次、顺序固定，不能只有标题和图而没有解释。需求层包含有内容的“验收/Acceptance”子标题，或 `<!-- ddd:acceptance -->` 后的验收说明/明确引用。

每种主图一个标记，直接接闭合的 text/ascii 围栏；flow/data 在概要层，state 在详细层。子图不重复主图标记。

````markdown
<!-- ddd:diagram flow -->
```text
[输入] --有效--> [处理] --完成--> [输出]
```
````

同样方式使用 `data`、`state`。不适用与尚未查清必须分开：

```markdown
<!-- ddd:diagram state not-applicable: 本功能为无持久或跨调用状态的纯计算；每次输入独立返回结果。 -->
<!-- ddd:diagram flow pending: 尚未读完失败回滚分支，需核对存储模块后再绘制。 -->
```

一个类别只能采用图、not-applicable、pending、ref 其中一种；`not-applicable` 不接受只写“无/不适用/无状态”，必须解释。原因是否真实仍需审阅。pending 在普通草稿检查中产生警告，accepted 或严格定稿检查不能隐藏它。

避免重复共享图，可用本地引用：

```markdown
<!-- ddd:diagram state ref: ../modules/storage.md -->
状态由存储模块负责，见 [存储状态转换](../modules/storage.md)。
```

被引用文件必须是存在的非历史受管文档，并包含对应类别的标记/图（允许有限引用链，禁止循环）。仅链接到标题不证明该标题真实存在，检查器不验证锚点。主文档仍需说明为什么复用该图；复杂独立设计用链接保持单一事实来源。

## 5. 渐进检查，不强制全库重写

| 场景 | 自动检查的行为 |
|---|---|
| 声明 layered-v1 的 observed/proposed | 缺章节/图等产生警告，可保存真实草稿，不自动批准 |
| 声明 layered-v1 的 accepted | 同类缺口报错；不通过状态或证据字段冒充设计完整 |
| 老文档未声明格式且本次未实质修改 | 保留正文，缺口汇总为 legacy 警告；安装和普通核对不强制迁移 |
| `--base REF` 识别新建/设计正文变化 | 要求采用 layered-v1；草稿警告，accepted 报错；删除格式字段也不能绕过比较 |
| `--design` | 严格检查所有当前 feature/module；有 `--base` 时只严格本次受影响或设计变化范围 |

`--base` 的正文变化判断是文本启发式，尽量排除头部/证据更新，不是语义等价判断。纯代码修复不自动要求所有旧设计重写；定稿时用 `--base REF --design` 主动核对本次范围。无 Git 无法推断文档创建时间，使用显式格式字段与 `--design`；不能声称检查器发现了全部新文档。

```sh
node "$SKILL_DIR/scripts/check-doc-set.mjs" . --base origin/main --design
```

把基线换成项目真实比较版本。没有 Git 可用 `--design` 做全当前文档审阅；若当前只允许少量修改，保留其余诊断，不为“全绿”批量改正文。`--release` 的确认/实现/证据要求仍独立，不能替代定稿检查或真实讨论。

`stats.design.status` 为 `not-assessed`、`incomplete` 或 `structure-passed`；`semantic` 固定为 `not-assessed`。脚本只核三层、简单占位、图容器/位置/连接符、引用和原因是否存在，**不证明状态机正确、分支穷尽、图与代码一致、问题已被主动挖掘或用户真实批准**。

旧文档保持原始 Doc-ID、批准来源、正文、链接；只在获准范围补结构。纯结构整理不等于改变获批行为；发现旧结论有问题，先讨论再改。永远不调用安装器“修复”设计正文。
