# agent 升级导航：工具包、项目入口、项目设计分开处理

用户说“升级文档驱动开发 / 基于文档开发 / doc-driven-development”，立即采用本页，不进入普通需求讨论，不要求用户先设计升级脚本。明确的升级请求可以授权正常受管更新；预览不越界且没有本地冲突时继续 apply，不再问同一个“是否升级”。

## 先确定正在升级谁

查明用户指定的新包位置/版本、当前项目根、当前会话实际加载位置、项目 `.doc-driven/install.json`、规则文件及已有配置。区分用户级安装与项目本地安装；项目升级不等于全局/其他项目已升级。多项目不自动批量写入。

使用用户提供的可信完整发行包，先检查 TGZ 成员只含单一根、无绝对/上级路径、无符号/硬链接/特殊文件，再安全解压到项目之外。不把压缩包直接覆盖解压到 `.agents/skills`，不在原包目录先手工改版本号。当前脚本不下载或声明网络最新版本；只有旧包时应报告缺新包来源，不反复运行旧安装器声称升级。

从**新包**执行 `check.mjs --no-tests` 核对自身清单，再运行新包的升级入口：

```sh
NEW_SKILL="/实际安全解压位置/doc-driven-development"
PROJECT="/实际项目位置"
node "$NEW_SKILL/scripts/check.mjs" --no-tests
node "$NEW_SKILL/scripts/upgrade.mjs" "$PROJECT"
node "$NEW_SKILL/scripts/upgrade.mjs" "$PROJECT" --apply
node "$NEW_SKILL/scripts/doctor.mjs" "$PROJECT" --json
```

upgrade 复用已有 install 的备份、受管区块、归属、冲突停止与回滚，不新增第二套状态机；同样支持 host 等 install 参数，默认沿用已有收据。来源与已装版本相同是无更新/修复核对，不是发现了新版本；来源更旧则拒绝降级。未修改的 v0.2.4 及此前已支持版本可识别；本地定制冲突保留并逐项比较，不提供 force。

## 三类完成状态必须分别报告

**工具包与入口**：源版本、原版本、实际安装版本，改了哪些受管区块；未动哪些原规范。遵守 [INSTALL.md](INSTALL.md)，不覆盖 AGENTS/CLAUDE 原文、原 JSON、业务代码或设计正文。安装器可以更新索引自己的生成区块，不能重写人工导航。

**项目文档兼容**：默认只读检查/提出建议，旧规格继续保留。升级不批量生成 E、不改 Approval、不把 observed 改 accepted、不把未运行测试绑定新指纹、不跑项目迁移/数据库清理。配置中现有布局照旧；迁移目录是单独范围。

**会话加载**：文件更新不能刷新所有模型的上下文。当前 agent 明确重读项目实际新 SKILL 和相关指南、检查指纹；新会话再做 doctor --probe 实际探测。静态通过仍不能称所有 agent 都已加载，也不能忽略仍指向旧包的全局入口/嵌套规则。

## 项目文档怎样随版本演进

| 范围 | 处理 |
|---|---|
| 仅升级 skill（默认） | 不改项目设计正文；报告当前布局/格式诊断，不为让新工具变绿重写文档 |
| 用户同时要求可读性优化 | 在明确文档范围内改自然标题、解释和图，保持契约含义/身份/历史；复核真实入链，不再次索取同范围授权 |
| 用户要求整理/拆分设计资料 | 先展示路径与归属映射；原请求已覆盖且无歧义则按范围执行，结构性变化不自动成为新业务决策。超范围搬迁/删除仍需确认 |
| 新业务含义或实现改变 | 按共同设计和实施闭环；不能以“升级模板”绕过批准 |
| 旧证据与新内容不匹配 | 保留当时记录；针对当前需要核对/执行真实验证，不批量刷新 hashes |

没有固定“400 行必须拆”的新门禁。先折叠/链接重复证据、按阅读职责拆开，保留需求/概要/详细的清楚导航；不要每升级一次给所有功能增加几十行仪式字段。若项目自己明确规定行数，遵守或说明冲突，不能由 skill 擅自废除。

自然标题隐藏编号的迁移是可选；见 [COMMUNICATION.md](COMMUNICATION.md)。不删除稳定 ID，不因 ID 外观变化创建新需求。只改完全等价显示时无需重做业务审批，但要核对引用；改了含义仍需新决定。无法确定则只暂停该处，不阻塞纯工具升级。

最后用自然语言报告：工具是否更新、原规范是否保留、项目设计是否改变/尚待何种整理、当前会话是否已重读，以及真正的阻塞。不要把“技能已安装”“设计已迁移”“功能已实现”合成一个完成。


## 升到 v0.3.0 的验证迁移（与工具升级分开）

先用新包 upgrade 预览/apply，支持未修改的真实 v0.2.5；原规范、配置、设计正文、历史证据继续保留。工具升级不运行 verify/eval，不安装依赖、不创建业务验收计划、不把旧 E 改为已自动采证；测试权限和费用需要已有任务来源。

完成安装后当前 agent 重读新 SKILL.md 与 [VERIFICATION.md](VERIFICATION.md)。本次新增或实质修改且已要求实施的规格，建立真实验收约定与 runner-v1 计划，按已有授权运行；旧未修改范围仍保留历史格式及 records-only/not-assessed 提示。不让用户审批机器字段，也不因 v0.3 发布要求全项目回填。

`Runner-Receipt`/`Runner-Check` 只引用本次真实运行；`Verification-Format` 不可静默删除以绕过门禁。添加 profile 是检查约束变化，不是新的业务方案批准；若计划引入收费服务、生产访问或破坏性脚本，仍须单独明确新增边界。工具实现改变会使旧 runner 记录待复核，不能重算哈希伪装重测。

报告分四项：工具是否更新、原文是否保留、实际会话是否重读、项目测试是否运行。仅升级时最后一项应明确“未运行（不属于本次升级范围）”。
