# 概要设计模板

默认全局概要在 `<docsRoot>/architecture.md`；领域确需独立概要时在 `domains/<domain>/architecture.md`，导航可用该领域 README。见 [布局规则](../LAYOUT.md)。

全项目共享的结构与协作，不是技术栈或目录清单。不要求先掌握整个项目才能写薄版本；已分析范围与未知必须明确。

```markdown
# 系统概要设计

Doc-ID: ARCH-SYSTEM
Type: architecture
Revision: 1
Status: observed
Baseline: unknown
Owns: —
Implementation: unknown
Verification: not-run

## 摘要与范围
系统目的、外部参与方、明确边界、已分析与未分析的部分。

## 1. 领域与文档落点
| 领域 | 稳定职责/边界 | 功能规格目录 | 模块契约目录 | 现有资料与未分析部分 |
|---|---|---|---|---|
新布局为 domains/<domain>/features/ 与 domains/<domain>/modules/；旧布局填真实映射。
一个领域不等于一个包，概览不能替代功能和模块规格。

## 2. 模块与职责
| 模块 | 职责 | 对外接口 | 依赖 | 主要文档 |
|---|---|---|---|---|

## 3. 运行时协作与处理流程
用 ASCII 的 text 围栏展示重要用户请求/后台任务/消息端到端链路。
节点是步骤，箭头标分支条件；包含重要异常传播，不能只列模块名。
先用草图检查隐含假设，再将讨论结论整理进正文；说明同步/异步边界。
实际图可引用功能文档，不重复存第二份当前流程。

## 4. 数据流与状态归属
用 ASCII 数据流图标数据内容、转换、持久存储、读写可见性和责任主体。
谁创建、修改、读取、清理；跨模块一致性如何处理。
业务状态生命周期链接到所属功能/模块的详细设计，不用文档批准状态代替。
未查明的关系标未知并说明调查入口，不虚构容错或数据保证。

## 5. 依赖边界与公共约束
鉴权、错误、日志、配置、协议版本、资源限制等实际相关的横切规则。
已知的规则写来源；从代码推断的结构不能虚构成已批准架构。

## 6. 部署与运行边界
服务/进程拓扑、必要的外部系统、发布与迁移约束。
引用配置的实际入口，不复制容易变动的全部配置。

## 7. 关键取舍、未知与风险
已知理由与未知理由分开；待确认方案不得混入当前架构。

## 8. 验证入口
架构约束如何核对，执行了哪些检查，哪些尚未检查。
```

图规则与沿图走查见 [DESIGN.md](../DESIGN.md)，填写示例见 [导入示例](../examples/import-design.md)。图后解释关键前提与条件；历史架构若有矛盾要主动指出，不机械照抄。

默认 `Owns: —`，由功能/模块拥有具体代码；只有确有独立架构配置才给它主要归属，避免与所有功能重复。
