# 文档落点：统一布局，按责任创建最少文档

目录回答“这个功能属于哪里”，文档内部的需求/概要/关键详细设计回答“它是什么、怎样实现”。新项目默认在仓库根 `docs/` 集中维护，人和 AI 共用正文；`<docsRoot>` 取自项目配置，已有根和旧布局保持兼容。

## 1. 最小默认布局

```text
<docsRoot>/
  README.md                         项目导航 + 薄系统概览 + 生成索引
  domains/
    <domain>/
      README.md                     职责 + 关键概念 + 模块关系，按需创建
      features/<feature>.md         独立功能的需求/设计/验收，按需创建
      modules/<module>.md           独立模块的契约与关键机制，按需创建
```

先在项目 README 说明目标、外部参与者、领域关系和少量全局约束；单领域小项目可以先只用这一层概览。多领域或需独立阅读时，领域 README 说明范围、关键概念、模块表、状态归属和允许的依赖方向。简单模块可只在模块表中说明职责、公开入口和依赖；有独立状态、重要不变量或复杂公开契约时，再按 [模块模板](FORMATS/module.md) 创建独立规格，即使只有一个调用方。

模块表是设计摘要，不替代实施所需的可验证契约。简单局部模块的约束可放在现有功能规格；需要 runner 绑定或全量接管进度引用的行为必须有带 Doc-ID 的受管来源。独立后，概览只保留职责摘要与链接，不再复制规则。

配置中的 `index`（默认根 README）被受管规格扫描排除：这里写导航与薄概览，不定义独立 R/C、不声明代码 Owns 或绑定 runner。需要机器绑定的全局约束放独立 architecture/requirements；领域 README 确需纳管时可用 `Type: architecture`、`Owns: —`。普通导航不必添加规格元数据。

## 2. 扩展由内容触发

| 内容 | 何时独立及落点 |
|---|---|
| 系统/领域架构 | 概览无法清楚承载时提取到根或领域内 `architecture.md`；原处只链接 |
| 领域术语 | 定义较多且有独立阅读价值时提取到领域内 `glossary.md` |
| 长期重要决策 | 真实重大取舍才写 ADR；系统级在根 `adr/`，领域级在领域内 `adr/` |
| 变更提案 | 持续讨论、跨会话或复杂交付需要时在根 `changes/`；普通修复用已有契约和 PR 差异 |
| 接管进度 | 全量恢复按 ADOPTION 在根 `adoption/` 保留；普通开发不建接管报告 |
| 验证材料 | runner 计划按 VERIFICATION 保存，实际记录由运行器产生；共享复杂说明按需在根 `verifications/` |

不创建空文件套装。功能/模块沿三层格式，各节可以很短或解释性引用；architecture、ADR、change 使用各自格式。目录与阅读骨架统一，章节深度随职责复杂度裁剪。先减少重复，再按独立职责或契约拆分，不按固定行数拆文档。实例见 [模块与维护示例](examples/module-boundaries.md)。

## 3. 创建之前先决定归属

新独立规格的规范落点是 `<docsRoot>/domains/<domain>/features/<feature>.md` 和 `<docsRoot>/domains/<domain>/modules/<module>.md`。先读项目概览和已有领域导航，确定主要归属；领域名沿用稳定业务术语。

`domain` 是稳定责任分区，可对应已识别的限界上下文，但目录本身不证明领域建模。一个上下文可含多个实现模块；领域不等于包、任务或源码层。模块划分依据、状态所有权与契约见 [DESIGN.md](DESIGN.md)。

跨领域功能选择主要责任领域，引用其他领域的模块契约；同一规则只在一个主要位置定义。被许多领域调用不自动变为 shared：沿主要归属维护，确有独立平台职责才建立平台领域，解释边界。

领域概览不能冒充完整功能规格。不要创建 `docs/domains/orders.md` 后又把新功能放到 `docs/features/`，或用 `docs/domains/features/` 省略实际领域层。现有子文件夹保持兼容；新增分组应有稳定责任依据，不镜像整个源码树。

## 4. 配置与兼容

配置可选 `layout`，只有两种值：

| 值 | 含义 |
|---|---|
| `domain` | 新接入默认策略。当前受管 feature/module 位于所属领域的 features/modules；目录检查错误使 check-doc-set 失败 |
| `preserve` | 保留已有布局或迁移过渡；旧位置可用，不符合默认形状时诊断而不搬动 |

旧 `.doc-driven.json` 缺 layout 时按 preserve 读取，不写回 JSON。首次接入已有受管功能/模块时也默认 preserve 并提示。`install --layout domain|preserve` 只用于新配置，已有配置不覆盖。preserve 仍需在项目概览或已有索引登记真实归属，不生成并存副本。

新项目统一一个根；既有 docsRoots、自定义 docs-dir 与多个文档区域继续兼容。docsRoots 是实际资料区域，不是领域清单；不要把各 domains/<domain> 加成独立根掩盖错误层级。

## 5. 旧文档迁移必须单独授权

安装、升级、doctor、索引与检查均不移动设计。迁移先展示“原路径 → 目标领域 → 目标路径”，复用已明确覆盖的整理授权；未覆盖的新范围需确认。检查未提交修改和冲突，只调整获准范围。

保留 Doc-ID、条目标识、批准来源与正文；修复 Markdown 链接、Targets、Superseded by、源码可选指针、进度与索引引用，不复制第二份当前规格。迁移后明确采用严格布局才修改 layout，其余配置和原格式保留；不得放宽策略掩盖错误。

## 6. 工具与维护边界

check-doc-set 只核当前带 Doc-ID 文档的 Type 与路径形状，不推断业务划分、不强制空目录、不检查 superseded 的旧位置。doctor 的布局报告独立于安装状态；静态 ready 不证明设计质量，不通过重装修复正文。

正文、源定义、验证记录的事实归属与更新触发见 [REFERENCE.md](REFERENCE.md)。元数据或目录正确不能证明语义正确；相同职责的摘要、索引、AI 阅读材料都应链接当前主事实。
