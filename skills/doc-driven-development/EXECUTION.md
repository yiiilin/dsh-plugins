# 从已确认设计到可用功能：不让使用者反复推动

本页用于开发、修复、集成、委托执行与验收。不是把“写进文档”当作完成，也不是要求每个小任务建立工单系统。讨论规则见 [DESIGN.md](DESIGN.md)，人机表达见 [COMMUNICATION.md](COMMUNICATION.md)。

## 授权只确认新增差异，已确定事项自动继续

同时读取原始任务、已确认决定和当前规格。区分三个问题：业务/设计是否确认；本次任务是否要求实施；是否还缺真实环境或工具权限。

| 已有事实 | agent 下一步 |
|---|---|
| 原请求“实现/修复/做完 X”，随后同意 X 的具体方案 | 同一范围的实施意图持续有效；记录批准并实现、集成、测试、核对，不再问“要不要实现 X” |
| 用户明确“只讨论/只写文档/先别改代码” | 只保存设计，不能把同意方案解读为实施授权 |
| 已确认行为在代码里缺失，修复在当前实施范围内 | 缺失是执行任务，不是新业务决策；直接补齐 |
| 文档仍 observed，但真实历史批准已覆盖同一含义与修订 | 查证后补确认来源及状态；这属于维护记录，不把字段填写变成新审批 |
| 只有代码现状、grep、测试通过，没有真实批准 | 仍是 observed；不得批量转 accepted。若本次确需采纳，围绕实际行为提一次具体问题，不让人批准状态名 |
| 实施中出现新的外部行为、权限、持久化语义、不可逆操作 | 只就新增差异说明场景、影响及推荐；只暂停受影响单元 |
| 环境缺失、权限不足或调用接口缺失 | 先调查；已授权范围内可补的接线/私有适配继续做。只有新契约或无法自行解决的外部条件才升级，不把所有阻塞都变成“是否实现” |

真实批准可来自原任务、当前对话或仓库记录，不要求某个特殊口令。不明确的“好”只能绑定紧邻、清楚展示的范围，不能扩张为批准所有未决方案。确认记录不是 AI 给自己授权；测试结果永远不授权需求。权限、预算和用户停止指令继续有效。

任务阶段及继续行为：

```text
[已确认目标 + 原任务要求实施]
                  |
                  v
[列出当前范围所有重要行为和验收场景]
                  |
                  v
[开发] --> [接入实际入口] --> [真实验证] --> [双向核对]
   ^                |              |               |
   +------范围内缺失/偏差-----------+---------------+
                  |
                  +--新增设计选择--> [只讨论新增差异]
                  +--外部条件受阻--> [保存阻塞；继续无关单元]
                  +--全部满足------> [说明用户能做什么及验证边界]
```

每次阶段结束后执行下一项已授权工作，而不是用“下一步可以……”替代执行。到达真实阻塞/权限/预算边界或会话容量边界时保存实际成果、下一项及原因，不声称后台继续。

## 以最小可用行为切片，而非文件或编号清单

先定义一条用户可观察路径，再分开发、测试与集成责任。例如“提交消息后被正式派发”，不是“增加两个端口方法”。

```text
[正式入口] --请求/事件--> [调度/调用者]
                                |
                                v
                         [领域模块和持久化]
                                |
                                v
                         [真正的消费/输出端]
                                |
                                v
                         [用户可观察的结果]
```

对每条交付单元，在已有变更提案中保留：自然名称、原确认与实施授权来源、目标规格修订、所覆盖行为、允许修改范围、不可改变约束、入口和调用链、验收方法、依赖、执行者/集成人、当前状态和实际阻塞。小修用几行即可；涉及跨模块、正式入口接线或多 agent 分工时，必须使用下方可检查交付包（无工具环境保留同等信息并披露未检查）。不是每个函数都建任务，也不复制完整规格。

必须先覆盖本次获批行为，再派发；每项重要需求/约束都应有负责的单元。缩小范围、延期必须有真实来源，不能因为难测就自动排除。不以文档改了几篇、函数搜到几处或门禁错误减少代替产品进度。

## 测试设计前置，完成不能只看组件

设计时按 [VERIFICATION.md](VERIFICATION.md) 确定需求场景、模块交互与关键不变量对应的验证方法，分批实现并立即接线。“生产路径”是在已授权隔离环境使用实际装配，不等于可以访问真实生产服务；端口/字符串/SQL 列/组件测试存在不足以证明功能。

每个单元完成需同时满足：范围内无遗漏、入口到结果链路可达、必测实际运行、未引入未批准行为、当前规格与最终集成代码匹配。子 agent 的 passed 只是报告，集成人核对 diff、实际产物及最终装配；合并后执行必要集成/验收，不把分支绿色直接相加。

具体运行、计数、跳过、超时、旧版本、人工验收与资源边界只在 VERIFICATION 详述。无专用 E2E 可以用覆盖同一真实场景的集成检查/可核验演示，不能用静态或仅组件通过代替。未接通/未验证标 partial 或 blocked；仅已批准延期才排除，继续其他无关单元。

## 复杂交付的机器检查包；小修可简化

复用 `docs/changes/<本次变更>.md` 中一个折叠附录，**不要求另建数据库**。模板在 [FORMATS/delivery.md](FORMATS/delivery.md)。它引用规格而不复制正文；不能放在自身被 specRefs 绑定的文档中，避免递归指纹。没有复杂分工的小修沿用正文核对即可；跨模块、正式入口接线或多 agent 实施不能跳过交付单元的覆盖/完成核对。

```sh
node "$SKILL_DIR/scripts/delivery.mjs" . --packet docs/changes/current.md
# 先真正完成实现/测试/集成；--complete 拦截仍缺失/受阻/旧版本/跳过必测的单元。
node "$SKILL_DIR/scripts/delivery.mjs" . --packet docs/changes/current.md --complete
# REF 是本次真实比较基线；只选择当前范围，不要求整个旧项目都 complete。
node "$SKILL_DIR/scripts/check-doc-set.mjs" . --base REF --design --release --delivery docs/changes/current.md
```

状态 queued/implementing/integrating/verifying/done/blocked 是机器字段，用户报告用“待执行/开发中/正在接通/验证中/已验证/受阻”的自然表达。缺授权或授权变更不能仅改 mode/source 绕过；delivery/check-doc-set 不判断口头批准真实性，也不启动 worker 或测试；verify 是单独的显式执行入口。

检查默认展开绑定文档的全部 R/C。仅实施其中一部分时，用 selectedItems + scopeSource 记录原授权的小范围；deferred 要有原因和真实批准。工具能防止**声明范围**里遗漏单元，不能证明 AI 声明了所有业务需求；主 agent 仍要从原始目标核对分解是否完整。

## 资源和安全也有边界

数据库迁移、部署、删除卷/数据、安装依赖等按项目明确权限执行。**匿名 Docker 卷不等于临时或可删数据**；禁止把全局 prune 当常规测试修复。只清理能证明由本次任务创建且获准删除的资源，记录资源标识、生命周期和清理结果；不能从卷名称猜测所有权。空间不足先检查并限制日志/构建开销，需要删除其他数据时单独说明并确认。重复两次通过不证明磁盘就是全部根因。
