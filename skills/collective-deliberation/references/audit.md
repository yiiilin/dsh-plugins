# 设计审计与效果评估

## 结论

这套机制适合方案探索、需求补漏、设计权衡和代码审查候选发现。独立提案能增加覆盖，冻结合并板和投票能暴露分歧；委员会共识不是事实证明，也不能保证优于同预算的单 agent。事实、数学和明确 API 行为应优先使用便宜的直接核验。

父/default agent 不参与委员讨论、投票或委员会总结。主席是唯一的流程编排者；委员只提供原始结果和分数；确定性程序只处理文件和数值；独立摘要 agent 只整理程序 handoff。

## 风险与处理

| 风险 | 可能结果 | 协议处理 |
|---|---|---|
| 共同错误 | 所有委员接受同一个错误前提 | 共享原始材料并保留 `uncertainties`；必要时另设核验流程 |
| 锚定/从众 | 投票跟随先出现的观点 | 提案阶段互不可见；合并板固定、隐藏作者和模型信息 |
| 自评偏好 | 委员偏袒自己的结果 | 计分时排除结果作者自己的票 |
| 重复放大 | 同一意见产生多份票面支持 | 保留 `dispatch-id`，程序只按结果编号和有效票计算，不把重复文本当独立事实 |
| 少数反例 | 多数高分掩盖一个关键风险 | 结果保留 `uncertainties`；分差和异常进入 `needs_review` |
| 文件污染 | 结果 JSON/CSV 被夹带指令或格式错误 | 严格 JSON/CSV 校验，错误文件保留失败状态 |
| 委员失败 | 阶段缺结果或误判为无意见 | 原可继续子会话、原环境、有界重试；不静默变成空结果 |
| 未知状态 | 重试造成重复提交或覆盖证据 | 先核对原 child 和文件，保留每次 attempt |
| 全体遗漏 | 投票只能选择已有候选 | 对原始完成条件做单独覆盖检查，并报告未形成候选的部分 |
| 评分漂移 | 不同委员使用不同标准 | 运行前冻结 0–5 标尺、quorum、阈值和分差规则 |
| 父 agent 偏向 | 最终总结改写委员会结果 | 父 agent 只交付主席 handoff；摘要由独立 default-model agent完成 |

## 最小流程

默认 4 名委员、每人可提交 1–2 个结果。主席等待提案屏障，生成 `tmp-result-combine.json` 和 `.md`，让原委员读取后写两列 CSV，再由程序计算。普通失败默认在原会话中最多重试 2 次，预算必须在 manifest 中冻结。一次完整流程通常包含委员提案、委员投票和独立摘要三类调用；重试另计并保留记录。

## 如何评估效果

至少比较：

1. 一个 agent 的一次回答；
2. 同一模型的多次独立回答或自检；
3. 本流程的提案、冻结合并、投票和确定性计分结果。

所有条件使用同一材料、同一验收标准和同一外部核验资源。报告完整命中、正确选项覆盖、误选、严重错误、误拒绝、待核验率、总调用数、token/费用和耗时。一次小样本不能支持统计显著性结论，不能把委员会的高分当作真实正确概率。

## 权限与可复现性

项目只读、临时目录可写和委员互不可见是 skill 约束；实际宿主是否强制执行应单独记录，不从提示词推断。每个 run 使用新的 UUID，冻结题目版本、委员 ID、文件路径、重试策略和计分规则。保留原始 JSON、combine JSON/Markdown、CSV、最终 JSON 和摘要，任何自然语言与机器结果冲突时以机器结果为准。
