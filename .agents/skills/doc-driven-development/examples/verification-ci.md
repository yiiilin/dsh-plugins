# 接入已有 CI（只提供示例，不自动修改项目）

沿用原 CI 的 Node、数据库及依赖准备方式。把计划、验收断言、适配器和工作流变更放入正常审阅范围；不要让实现 agent 为了变绿自己取消必测。执行器不是沙箱，运行未受信任 PR 时尤其不能给生产凭据或特权运行器。

本 skill 不附带可执行脚本，因此 CI 阶段要由你自己接线。以下是 POSIX shell 阶段的**示意结构**，路径与命令必须替换为实际项目；所需环境由受保护 CI 提供：

```sh
set -eu
PLAN="docs/changes/actual-task.verify.json"

# 1. 只读预览：人工核对计划、适配器与断言的实际差异，并记下计划指纹。
#    这一步不得执行项目代码，也不得创建运行目录。

# 2. 执行：用上一步记下的指纹核对「将要跑的就是刚看过的那份计划」，然后运行计划里的检查。
#    检查命令、工作目录、超时与输出上限都以计划字段为准。

# 3. 采证：为本次运行建立独立目录，保存每个检查的 stdout/stderr 与实际判定。
#    每次运行的目录各不相同，历史运行不覆盖。
```

这三步的**内容**是约束，**命令**不是：用什么程序实现由你决定，但阶段划分、指纹核对和独立运行目录不能省。

这是实际执行与采证阶段，不会自动更新仓库规格。提交前核对摘要输出，将实际 Verification-Receipt 放在规格头并维护状态；交付包引用 runs，不再复制完整证据记录。然后执行本次范围的设计/发布/交付检查。CI 重新运行产生的是独立运行记录，不假装旧的本地运行路径能在另一台机器天然存在。

历史证据在本地只保留引用、CI 产物下载缺失时，原文档静态检查可能提示本地工件缺失；不能通过虚构路径或改 Evidence 字段消除。可在可信 CI 中取回对应产物后核验，或为本次结果生成新记录。本 skill 不是云端工件服务，不自动上传、下载或认证签名。

发布时分开说明：文档/设计检查、实际项目运行、范围覆盖、人工待验收和外部环境限制。使用 CI 的 always/失败保留机制保存失败日志，但先审阅和脱敏，不将所有 stdout 不加区分公开上传。禁用不相关可选测试必须有明确范围依据；必测被跳过不能由 CI 总 exit 0 覆盖。

参考 [GitHub Actions 安全强化指南](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions) 的工作流审阅与隔离原则；这里只是宿主无关的执行阶段，不表示已经给用户仓库配置 CI。一般运行流程见 [WORKFLOW.md](../WORKFLOW.md)。

## 失去的机械保证

「预览 → 指纹核对 → 执行 → 采证 → 判定」的一条命令已随脚本移除：**预览指纹与实际执行的绑定现在靠人，写错一个字符不会报错**。CI 里要保住这道门禁得自己实现指纹比对。逐项对照见 [WORKFLOW.md](../WORKFLOW.md) 末节。
