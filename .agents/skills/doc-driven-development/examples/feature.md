## 摘要

**假设方案**，示范三层正文与 ASCII 图。不来自真实仓库，没有实现，也没有人的实际批准。

假设需求：导入失败时不留下业务可见的部分数据。候选方案为"先校验暂存，再事务发布"，同一请求标识用于查询最终结果。AI 主动提出"提交成功但响应丢失"场景——此时结果不明，不能当作失败。以下展示该讨论如何落成文档。

不包含断点续传、发布后撤销、跨库分布式发布。实际项目需先确认接口、数据规模、故障恢复能力，不能只换名称就实施。

## 1. 需求说明
<!-- ddd:section requirements -->

### 1.1 使用者与范围

操作者提交文件，业务查询方读取已完成导入的数据。状态查询和错误信息只对有权限的调用者开放。

### 无部分结果
<!-- ddd:item R-DEMO-IMPORT-001 -->

任一行非法或发布明确中止时，本批次不产生业务可见的部分结果。全部成功后数据整体可见；"清理尚未完成"不改变可见性。

### 结果不明与重复请求
<!-- ddd:item R-DEMO-IMPORT-002 -->

提交结果无法确定时，调用方得到"处理中/结果待确认"及可查询的批次标识，**不得被告知已失败**。同标识同内容重发返回已有任务；同标识不同内容拒绝并说明冲突。

### 1.4 验收条件

首行和末行非法时都读不到部分数据；合法文件完成时全部可见。发布提交后响应丢失，用原标识查询应得到最终成功且不重复写入。结果不可判定时不能误报失败。不同内容复用相同标识被拒绝。

**以上是验收计划，不是已执行结果。**

## 2. 概要设计
<!-- ddd:section overview -->

### 2.1 职责与边界

入口负责认证、请求标识和参数校验；导入处理器负责解析校验与暂存；存储模块拥有任务状态与批次数据，负责事务发布；结果核对器查询权威提交事实。业务查询必须通过可见性边界，不能绕过存储模块读到未发布记录。

候选前提：任务状态、批次数据和可见性判定处于同一具备所需事务能力的存储系统。若不满足，应返回讨论，而不是自行改成最终一致性。

### 2.2 端到端处理流程
<!-- ddd:diagram flow -->
```text
[提交请求] --身份及参数合法--> [查找请求标识]
                                  |
                                  +--同标识不同内容--> [拒绝冲突]
                                  +--同标识同内容----> [返回已有任务]
                                  +--新请求--> [创建任务并校验暂存]
                                                    |
                                                    +--失败--> [明确失败；不发布]
                                                    +--完成--> [事务发布]
                                                                  |
                                                                  +--已提交--> [成功]
                                                                  +--已中止--> [失败]
                                                                  +--结果不明--> [按原标识核对]
                                                                                     |
                                                                                     +--仍不明--> [保持处理中]
```

身份或参数不合法在入口直接拒绝，不创建批次。**"暂时未查到"不足以证明中止**，核对不盲目重放发布写入。

### 2.3 数据流与归属
<!-- ddd:diagram data -->
```text
[调用方] --请求标识 + 文件--> [入口/导入处理器]
[入口/导入处理器] --内容指纹 + 标准化行--> [存储模块]

[存储模块] --暂存写入--> [批次数据区]
[存储模块] --任务及发布状态--> [任务记录]

[批次数据区] --批次行数据--> [业务查询]
[任务记录] --已发布批次条件--> [业务查询]
[业务查询] --可见数据--> [业务调用方]

[任务记录] --权威状态--> [结果核对器]
[结果核对器] --批次标识 + 可确认结果--> [调用方]
```

任务记录和批次数据都归存储模块；发布改变可见性条件，不搬运所有行。查询能否以所需一致性读到状态与行，须由具体存储实现保证，**不能仅靠图上的箭头**。

### 2.4 方案与代价

暂存后发布避免把整个文件读取放进长事务，但增加暂存空间、状态存储、查询过滤和清理机制。**不虚构吞吐量、超时或保存天数。**

## 3. 详细设计
<!-- ddd:section detail -->

### 3.1 接口与数据契约

候选逻辑接口为 `submit(requestId, file)` 与 `getResult(requestId)`。请求标识唯一性由持久化约束保证，**不依赖进程内"先查再插"**。相同标识的内容比较必须定义稳定指纹算法，不能只比较易变文件名。传输协议、文件大小和保留期无来源，列为待确认。

### 3.2 业务状态流转
<!-- ddd:diagram state -->
```text
[NEW] --开始解析--> [STAGING]
[STAGING] --校验或暂存明确失败--> [FAILED]
[STAGING] --全部输入校验和暂存完成--> [READY]
[READY] --取得发布执行权--> [PUBLISHING]
[PUBLISHING] --发布事务确认提交--> [SUCCEEDED]
[PUBLISHING] --发布事务确认中止--> [FAILED]
[PUBLISHING] --超时或提交结果未知--> [PUBLISHING]
```

状态归存储模块；修改需要合法转换和并发控制。最后的自循环表示暂不能确认结果，**不能覆盖写回而回退已成功状态**。权威状态必须单调，核对器查询而非凭超时推断失败。

| 转换 | 守卫条件 | 关键动作或限制 |
|---|---|---|
| STAGING → READY | 全部输入校验、暂存完成 | 固定本批次内容，不接受"半完成即发布" |
| READY → PUBLISHING | 状态仍为 READY，取得唯一发布权 | 条件更新/等价串行化，不让两个进程同时发布 |
| PUBLISHING → SUCCEEDED | 存储事务提交事实成立 | 可见性切换与成功状态必须原子关联 |
| PUBLISHING → FAILED | 可证明发布已中止，不会再晚到提交 | 不能仅因超时或查不到成功记录而失败 |

### 发布与错误不变量
<!-- ddd:item C-DEMO-IMPORT-001 -->

暂存写入不对业务开放；发布前验证任务处于允许状态、输入已完整。事务内原子改变可见性和最终成功状态，**不能先暴露数据再异步补成功记录**。事务失败需区分"已确认回滚"与"结果不明"，后者不向调用者伪报失败。

并发发布、重启后执行权回收、数据库错误分类依赖具体存储能力，落地前必须补齐可执行细节；**未确认的恢复算法不能由 AI 默默选择**。

### 3.4 清理、核对与实现自由

失败批次可按明确策略清理暂存数据；清理失败只影响资源回收，不改变可见性。核对需有界频率与停止条件；超过预算仍未知时，停止自动轮询并**显式转交人工核对**，不擅自改成失败。

不影响上述接口、状态和不变量的私有函数拆分、局部命名可以自主；哈希算法、保留期限、故障恢复不属于同一级别的命名自由。

### 3.5 待讨论问题

- **D-DEMO-IMPORT-001**：界面是否允许返回处理中及查询入口？业务裁决点，尚无批准。
- **D-DEMO-IMPORT-002**：真实存储能否保证可见性切换、最终状态与读取视图一致？需调查验证。
- **D-DEMO-IMPORT-003**：故障后执行权如何回收，未知提交怎样得到确定结果？当前只建立问题与约束。
