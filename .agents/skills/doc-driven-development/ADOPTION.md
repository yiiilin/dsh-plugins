# 已有项目接管：渐进与全量

两种模式都支持。**全量是完整的范围承诺，不是一次把所有源码塞进上下文，也不是一次性生成看似完整的摘要。** 以实际读过的代码、接口、配置和测试为依据，多批分析并持久保存进度。整个过程不自动修改业务代码。

## 1. 共同起点

读取项目规则、工作树状态、已有文档和运行入口。默认不改业务代码，但必须主动识别逻辑缺口与矛盾；"只记录现状"不等于"不得思考或提问"。事实先自行查证，对影响当前任务的重要缺口按 [WORKFLOW.md](WORKFLOW.md) 给出具体场景、后果与讨论建议；未获授权不实施改进，候选改进放独立提案，不混入 observed 现状。用户明确只要静默盘点时保留问题清单，避免不必要打断。

保留原有文档位置和语言，映射而非强制迁移。项目级接管先按 [README.md](README.md) 第 1–2 节完成接入检查，缺安装时按同页完整流程；不能靠写一个启用配置项代替安装。用户禁止安装或只允许文档修改时，仅执行临时流程并说明未接入。按 [FORMATS.md](FORMATS.md) 确定全局文档根与领域落点映射；新建文档默认 `docs/domains/<domain>/features/` 与同领域 `modules/`，领域概要不能替代具体契约，旧布局只映射、迁移单独确认。

先建立文件盘点和内容快照。盘点只列路径、分类、哈希与结构归属，**不会理解项目，更不会自动写出设计或把文件标记为已读**；手工盘点要保留等价清单并说明哪些项未作哈希检查。默认不读取密钥、`.env`、依赖缓存、构建结果、符号链接目标和明显二进制，Git 忽略内容不进入默认候选，排除范围必须列入接管报告。遗漏生产所需生成协议、数据库 schema 或部署配置时补读安全的源定义；忽略规则不是架构上"不重要"的证据。

## 2. 渐进接管

先在项目/领域 README 建立薄概览和本次契约导航；仅长期独立功能或复杂模块才拆规格，不要求整库规格完备。根配置 index 不能作为受管规格或 progress 引用。

每次任务执行：定位所改功能及直接上下游；阅读业务入口、核心规则、状态存储、失败路径、关联测试与配置；恢复这部分 `observed` 文档，绘制实际流程/数据/状态图；发现隐含假设主动提出讨论；区分现状与本次目标；只确认本次必要约束；实现、验证并更新归属与覆盖账本。这里的"一层邻居"是起点而非硬上限——事务、权限、协议或状态跨越更多层时沿正确性依赖继续追踪，不能为节省阅读而留下当前修改所依赖的核心规则未知。

没有触及的区域允许保持未分析，不为此创建空白详细设计，也不让整个项目的未知阻塞局部维护。随后每次维护扩大可信范围。

## 3. 全量基线：按批次做完约定范围

**不是扫描过就算读过。** 只有确实读完文件、并分析了相关职责与约束，才能记为已读；不得悄悄把全量目标缩小成当前文件、当前批次或一份摘要。

### 阶段 A：盘点与边界

列出所有包、服务、应用入口、后台任务、数据库/持久化、外部协议、配置、部署/发布规则和测试集合；明确候选文件总数、排除策略、无法读取项和纳入范围，不用文件数量推断功能完成度。在项目/领域概览列出"领域 → 职责 → 功能目录 → 模块目录 → 现有资料"，薄内容合并到 README，复杂内容才独立 architecture；全量任务保留接管报告与 `docs/adoption/progress.json` 的实际分析进度。依赖明确时先读公共契约再读功能链；progress 必须引用受管来源，不能只写包摘要或未纳管导航就声称完成逆向。

### 阶段 B：模块与关键链路

每批按稳定功能/模块读取真实代码，不按任意文件数切断业务链。记录职责、公共接口、状态所有权、关键依赖、关键状态转换、异常、并发、事务、资源限制和当前测试覆盖；至少追踪真实存在的正常路径、失败路径和跨模块路径，鉴权、写入一致性、重试/幂等、发布/迁移等适用路径单独核查。不适用的项写原因，不编造系统没有的机制。对关键断言记录文件+符号/配置字段+快照，必要时加行号但不只靠易失行号；目录名和注释只能是线索，不能代替对执行路径的阅读。

### 阶段 C：逆向成三层设计

在功能文档中分开：**现状行为**（代码/测试/运行中实际观察到的行为及证据）；**需求来源**（来自用户或可信现有规格的需求，仅从实现推断的意图标"推断，待确认"）；**概要与关键详细设计**（代码实际结构和机制，无法恢复的"为什么"写未知）。

静态可见的重试次数是事实；"为满足某个服务承诺而设定"通常需要其他来源。测试断言可以说明历史预期，不自动证明业务正确。性能目标与实测性能分开。坏味道、疑似 BUG、死代码、文码冲突进入风险清单，不在基线梳理中顺手重构。

图用于分析，不是收尾装饰：概要画处理流程和数据流，详细设计画业务状态转换，每条关键断言关联源码入口；未找到的分支标未知并记录调查路径，不补想象中的容错机制，部分分析可标 pending 并保留真实缺口。每批选择真实正常、失败、重复/边界场景沿图走查，把逻辑断点、无主数据、孤立状态和冲突的调用约定按主题记录并给讨论建议；影响本次变更的关键问题及时讨论，无关问题不阻塞其他分析，不要求一次批准全库。

### 阶段 D：跨模块核对

核对接口生产者/消费者、事件名、数据所有权、错误传播、版本/兼容性、关键依赖方向和部署配置。共享事实归入一个主要模块契约，功能文档引用，不建立互相矛盾的副本。有权限和隔离环境才运行验证，先检查命令副作用；未执行、失败和被环境阻塞都记录原样，不把静态推断写成实际运行通过。

### 阶段 E：完成基线，而非自动批准系统

刷新盘点清单，检查进度中的源码哈希是否变化；对变化文件重读，并评估调用者、约束和旧证据是否受影响。整库快照变化不意味着重做所有批次，但也不能只机械重读变更行。只有纳入范围内每个候选文件都已实际检查、或明确排除并记录理由，才称"约定范围全量分析完成"。高风险未知、未验证性能和无法恢复的意图可以继续未知，必须在交付显著展示，不会因为覆盖完就消失。

完成时交付：架构导航、功能/模块文档、要求—实现—证据入口、范围/排除清单、未知与冲突、后续接管入口。文档仍可为 `observed`；邀请人按主题采纳，不要求一次批准全部历史实现。

## 4. 可续接的机器进度

`docs/adoption/inventory.json` 是扫描快照；`progress.json` 是模型/开发者实际阅读后的记录，两者不能混同。

```json
{
  "schemaVersion": 1,
  "inventorySnapshot": "<扫描快照中的原值>",
  "files": {
    "src/import.mjs": {
      "sha256": "<扫描快照中该文件的 sha256>",
      "state": "reviewed",
      "docs": ["docs/domains/data-import/features/import.md"],
      "note": "已追踪调用方、错误路径和事务边界；设计理由仍未知。"
    },
    "tools/local-demo.mjs": {
      "sha256": "<该文件的 sha256>",
      "state": "excluded",
      "docs": [],
      "note": "一次性本地演示，明确不属于本次维护范围。"
    }
  }
}
```

`state` 允许 `reviewed / partial / blocked / excluded`，没记录就是未读。`reviewed` 至少链接一篇已有且带 `Doc-ID` 的非历史文档；`excluded` 必须解释，不用 `Owns: **` 或自动批量写 `reviewed` 凑覆盖率。大文件/二进制没有文本哈希时不得标 `reviewed`，应说明排除理由或采用适合该格式的专用审阅并单独记录。

按 `progress.json` 逐项核对范围账目：进度记录、引用和当前快照在结构上是否成立。结构成立只说明账目自洽，不证明模型真的理解了每个文件，也不把 `observed` 升为 `accepted`；旧路径删除、哈希改变或快照过时都要在核对时主动指出。

## 5. 中断、换模型与新增修改

每批结束保存已写文档、真实阅读记录、未解决矛盾、当前快照与下一批具体入口。下次先比较新盘点与各文件哈希，再继续；不要仅凭"上次完成 70%"接手。本次会话容量不足时，交付已完成内容及准确剩余范围，不说完成，不承诺后台继续；恢复可以在下一次显式调用中进行，不能要求用户重新叙述已有记录。接管后进行正常开发时，主动讨论缺口、整理结论、确认实际差异再实现；历史观察逐步采纳，现状文档与目标文档不能互相冒充。

## 6. 即时记录、当前上下文与评审

渐进接管沿本次功能链及时记录已确认决定，保留观察/约定之分。全量恢复按批保存事实、推断、疑似缺陷、未决主题与下一步；发现问题主动探讨，但不每个未知都停掉整库分析。用 [WORKFLOW.md](WORKFLOW.md) 在阶段切换/恢复时核对文档和代码变化；盘点快照与 progress 继续记录真实阅读，**快照不替代阅读账本**。

批次完成做跨文档/接口一致性审阅；高风险优先独立只读评审，主 agent 查证问题后整合。引用 [WORKFLOW.md](WORKFLOW.md) 的解释顺序，先让人理解场景再裁决。观察通过审阅仍是 observed，不自动 accepted；只文档接管不跑 release 冒充实现完成。旧证据可留作历史，新验证和评审绑定实际规格/代码版本，不批量刷新旧通过结果。

## 7. 接管不能让已经确定的开发停在元数据维护

原请求包含实施时，已确认的行为和约束按 [WORKFLOW.md](WORKFLOW.md) 继续落实，不反复询问同一批准；仅分析的接管仍只读/写文档。旧文档 observed 与真实确认不一致时核对历史来源后维护字段，不能用 grep 或代码"看起来实现了"批量接受需求。目录/格式维护不要求把全库变 complete；升级不移动项目文档正文，见 [README.md](README.md)。

仅现状分析不自动运行项目脚本，也不把 observed 改为 accepted。已有验证记录可保留来源，未亲自执行的不改为运行记录。接管盘点覆盖不等于测试覆盖。

## 8. 接管报告骨架

全量基线需要，渐进接管可只保留简短范围与下一步；路径可适配已有布局。实际控制/数据/状态图放在对应功能或模块，不在接管报告复制全套。

```markdown
# 项目设计恢复记录

Doc-ID: ADOPTION-PROJECT
Type: adoption
Revision: 1
Status: observed
Baseline: unknown
Owns: —
Implementation: not-applicable
Verification: not-run

## 目标与范围
模式：渐进 / 全量。本次仅记录现状，不修改业务代码。
纳入路径、功能边界、排除项及理由；已有文档如何映射。新布局为 domains/<domain>/features/、domains/<domain>/modules/，旧布局迁移需独立授权。

## 代码基线与盘点
实际 Git 提交/工作树情况、inventory 快照；候选/已读/部分/受阻/排除的数量与分母。文件映射覆盖不等于语义理解或正确性。

## 阅读导航
先读项目/领域概览，再读本次功能与模块契约，最后看风险和验证记录。薄概览合并在 README；`<INDEX_PATH>` 指向的索引不供受管进度或验证计划绑定。

## 分批进度
| 范围 | 实际已读文件/入口 | 产出文档 | 当前状态 | 待解事项 |
|---|---|---|---|---|

## 跨模块核对
接口、数据归属、异常传播、鉴权、迁移/发布等适用的关键检查。

## 未知、冲突和疑似缺陷
事实、推断、待确认意图分开。标注影响与证据，不顺手重构。

## 已执行验证
实际命令/步骤、环境、版本、结果、不能验证的内容。

## 本次交付与继续入口
明确已完成和未完成范围；下一批从哪个入口继续。全量未结束时不得写"全项目分析完成"。
```

每批报告按主题列出：已查明事实、缺失/矛盾、调查依据、影响、建议讨论的问题和下一步。未知分支如实标注，无关问题不阻塞其余分析。全量覆盖完成不等于批准这些历史行为。
