# doc-driven-development

通过文档讨论重要设计，再把已授权方案落实到实际运行行为。**纯方法论：只有文档、模板和例子，没有脚本**，不规定用什么工具；不需要 Node.js、网络或额外依赖。日常任务路由见 [SKILL.md](SKILL.md)。

## 1. 接入：两件手工动作

**只复制目录、或只写规则块——单独任何一件都不算接入。** 两件都做完才算。**不存在需要写的启用配置**：写入规则块本身就是启用。

**一、skill 目录到位。** 把整个 `doc-driven-development/` 复制到宿主的技能发现路径，目录名不要改（规则块和 skill 内部都按此名引用）：

| 宿主 | 发现路径 |
|---|---|
| DSH | `.agents/skills/doc-driven-development/` |
| Claude 系 | `.claude/skills/doc-driven-development/` |
| Codex 系 | `.codex/skills/doc-driven-development/` |

`.agents/skills/` 只对确实扫描该路径的宿主有效，**不是通用约定**；无法确认时靠规则块显式要求读取 skill 路径。**同一项目只留一份副本**——两份会立刻漂移。装到用户级时也要选定唯一维护源，其余位置由它复制而来。

**二、写入口规则块。** 复制 [规则块模板](FORMATS.md#57-rules-block项目入口规则块) 模板整段（含首尾标记）到项目入口文件末尾，替换 `<SKILL_PATH>`、`<INDEX_PATH>`、`<LAYOUT>` 三个占位符，写完自查三者都能解析到真实文件。**写入规则块即表示启用**，不依赖配置文件。

入口文件：已有根 `AGENTS.md` 就写它；Codex 有非空 `AGENTS.override.md` 写它，否则写 `AGENTS.md`；Claude 系写 `CLAUDE.md` 或 `.claude/CLAUDE.md`；多宿主共用时每个入口各写一份、内容相同，不要各写一套。

**只追加，不覆盖。** 已有规范不删除、不改写、不重排；标记之外的原文逐字节保留（含 CRLF、BOM、无末尾换行等写法）；区块与原文冲突时停止，人工处理；同一入口只保留一个规则块；已有手工写的 doc-driven 规则保留并提示，不要按关键词猜着删。写之前先 `git commit` 或复制一份入口文件。

## 2. 生效检查

安装完成后**开新会话**再测——正在安装的会话已经从你的请求里知道了 skill，证明不了下次会自动加载。在新会话里问一个与该 skill 无关的普通开发问题，观察：规则是否真被加载（不是只声称文件存在）、agent 是否去读 `SKILL.md` 与文档索引、重要行为变化是否先给设计和确认、是否引用而非覆盖现有规范、没跑测试是否如实说未验证。

**一次通过只代表这一次、这一个宿主**，不保证其他模型、未来会话或子目录。入口规则是**行为指引，不是权限强制**，约束不了宿主给 agent 什么工具权限。

## 3. 升级

**升级只有两个动作：替换 skill 目录、人工比对入口规则块。** 规则块文字有更新时替换受管段落、保留项目自行增补的内容；项目文档正文不因升级而移动或重写；冲突时停止，人工合并。

先查明升级的是哪一份（用户级还是项目本地；项目升级不等于全局或其他项目已升级，多项目不自动批量写入）。**动手前先提交或备份 skill 目录和入口文件**——没有回滚，也没有强制覆盖的替代品。来源与已装版本相同是核对、不是发现新版本；来源更旧则拒绝降级。

**从压缩包升级时先检查成员**：只应含单一根目录，**无绝对路径或上级路径、无符号/硬链接、无特殊文件**，然后解压到项目之外再替换。**不要用重写 `AGENTS.md`/`CLAUDE.md` 代替安全替换**；已有规则与设计正文不得因套模板而整篇覆盖。升级后**不能忽略仍指向旧位置的全局入口或嵌套规则**。

**升级不新增仪式。** 不要每升级一次就给所有功能增加几十行仪式字段。若项目自己规定了文档行数或拆分门槛，遵守它，或说明冲突，**不能由本 skill 擅自废除**。

文件更新不刷新已有会话的上下文，升级后要在**新会话**里重新确认加载。报告分开说：工具包与入口是否更新、原规范是否保留、项目文档是否改变、当前会话是否重读、真正的阻塞。不要把"已安装""已迁移""已实现"合成一个完成。

## 4. 卸载

删掉入口文件里 `<!-- doc-driven-development:begin -->` 到 `end` 之间的整段，再删 skill 目录。**项目文档、配置和备份一律保留**——卸载不等于清除项目设计资料。

## 5. 验证 skill 自身

改了这套方法论之后，怎么知道它还是对的。三类验证不要互相替代：**文档自洽**靠人工通读加宿主搜索工具（链接有效、模板与 [FORMATS.md](FORMATS.md) 字段定义一致、必测与状态语义不矛盾、人工写的正文没被改写）；**方法论有效**靠在真实项目上走一遍完整闭环，按 [WORKFLOW.md](WORKFLOW.md) 采证并如实标注受阻与待人工验收；**行为遵守**按[真实宿主评测起步集](examples/evaluation-cases.md)跑人工会话，审阅真实逐轮轨迹。

**改一处定义，就要查所有引用它的地方**：修订字段、状态、术语或流程后，回头核对引用它的表格、字段说明、摘要与流程图；尤其注意「执行／拒绝／通过／验证」这类承诺——确认谁执行、依据什么、产出什么证据。只改定义不查引用会留下自相矛盾的文档。

**检查本身也要验证**：从不报错的检查等于没有检查——把已知缺陷临时放回去，确认它**确实被检出**，再恢复。链接检查要**分开查目标和标签**（目标有效时标签仍可能指向已退役名称），并维护「退役名称 → 当前对应物」清单扫正文与标签。

**静态复核不当作运行验证**：通读"看起来没问题"不证明任何行为正确。跑一例是一次完整人工会话，不是一条命令；fixture 或少量全过不能当成稳定改善，也不能冒充真实 agent 效果。一次走通只代表这一次、这个项目。**不同模型不得共用一份结果冒充验证**；工具自测数量不等于真实开发质量或成本改善。

**仍未验证的范围（如实说）**：这次改造只做了**静态核对**（链接、锚点、字段与枚举齐全、与实例一致）与三轮文档审计。**没有在真实项目里走一遍完整闭环**，也没有做本页第 2 节的新会话生效检查，也没有跑第 5 节的宿主评测。因此「文档自洽」有证据，**「方法论有效」与「行为遵守」都还没有证据**。大仓库、多宿主、多模型的表现同样未测。**本地哈希只检测意外变化，不是防篡改证明**；验证流程不是沙箱。

设计借鉴 NASA 系统设计与产品实现、DORA 小批量、Google 代码评审、Anthropic agent 工程与上下文工程、Docker 资源清理等公开材料，只借用适用思想，**不声称符合任何认证**，**也不声称所有工具或环境都已兼容**，也不证明本版已减少真实项目成本。本 skill 不提供沙箱、不认证批准、不保证语义完整；高风险交付仍需受保护 CI 与独立评审。
