# 工作流程：读取事实、共同设计、实施与验证

本页是流程的唯一入口，合并了设计、实施、验证、上下文、多 agent 与沟通六部分。字段、枚举与记录格式见 [FORMATS.md](FORMATS.md)，文档落点见 [FORMATS.md 第 4 节](FORMATS.md#4-文档落点与布局)，接管见 [ADOPTION.md](ADOPTION.md)。

本 skill 不附带工具。本页规定**必须满足什么**；用什么程序、什么命令满足它，由你决定。

**事实来源**：Markdown 与代码。一切索引、快照、图谱都是可重建的派生结果，不另维护数据库版业务事实。

## 三类任务怎么走

先判断本次属于哪一类，再照对应行执行。

| 任务 | 该做什么 | 产出 | 怎么验证 |
|---|---|---|---|
| **正常变更**（新功能或重要设计变化） | 读当前规格与代码 → 有新增重要选择才讨论并即时记录 → 划分模块边界 → 整理三层设计 → 按已有授权实现并接通真实入口 | 更新后的 feature/module 三层正文（需求说明/概要设计/详细设计 + 图）；有跨会话决定时一份 `docs/changes/` 提案 | 必测场景在真实入口实际运行并记录；证据绑定规格/代码/输入/工具/输出 |
| **BUG 修复**（含等价重构） | 同时读原任务、真实批准、当前规格与代码实际行为 → 定位是代码偏离要求还是要求本身有问题 → 在范围内修代码并补回归 | 代码/测试改动；主契约只在外部行为、所有权、入口或依赖改变时才更新 | 复现原缺陷的场景先失败、修复后通过；实际入口可达；未引入未批准行为 |
| **已有代码接管** | 按 [ADOPTION.md](ADOPTION.md) 确定渐进或全量范围 → 读真实执行路径 → 逆向成三层 → 分批保存实际阅读进度 | 现状文档（可为 `observed`）、范围与排除清单、未知与冲突清单、进度记录 | 逆向结论逐条关联源码入口；本次获准实现的部分才按本页验证；接管盘点覆盖不等于测试覆盖 |

三类共同前提：**先读当前事实**（第 1 节），**确认与授权分开**（第 2 节），**完成由真实验证判定**（第 5 节）。

## 1. 读取当前事实

开始或恢复任务、从讨论进入实施、开始评审、交付前、切换主题，或发现外部改动时刷新：

1. 读项目规则、当前工作树、相关文档的修订与正文、必要的邻接契约。
2. 与上次已读范围比较。
3. 有变化就回读并判断影响；相关旧评审与证据标记为待核对。**三条纪律：**

- 旧聊天结论不是最新文件。不按“时间最新”用 proposed 覆盖 accepted。
- **现行规格回答期望，代码回答实际，提案回答准备改变什么。** 三者矛盾必须显式暴露，不要挑一个顺眼的。
- 没有变化，也不能把“已扫描”变成“已读懂”。记录的是实际读过哪些材料、什么版本。

**怎么查**（用宿主自带的文件读取与搜索即可）：
| 要查什么 | 怎么查 |
|---|---|
| 某概念在哪定义 | 搜 `Doc-ID`、条目编号（`R-`/`C-`/`D-`/`E-`）、术语原文 |
| 某文档依赖谁 | 读它的 `Depends on`、`Targets`、`Covers` |
| 谁依赖某文档 | 全局搜该文档的 `Doc-ID` |
| 某文件归谁管 | 搜 `Owns:`，匹配路径 |
| 某条要求现状 | 读当前规格正文，再对照代码实际行为 |

中文短词按字面子串搜，不依赖分词。代码的调用、导入、影响面优先用代码图谱工具；**代码图谱只回答代码事实，回答不了文档关系**——“该不该依赖”是要求，图谱只说明今天有没有这条边。

**关系只用少量明确声明**：`Depends on` 写当前文档或条目 ID，来自实际设计依赖并在正文解释理由；它**不是代码导入允许表**。`Owns` 只认领主要实现，不表示拥有所有引用源码或写入权。一个模块只有一个主契约。

**影响分析**沿显式关系反向遍历（`Depends on`、`Targets`、`Owns`、证据引用）；普通链接只算 `reference`，不推断强依赖。变更判断保守：文档整体指纹变了就当它变了。合并新旧关系才能发现被删除的关系。循环图有限深度遍历，不伪造全覆盖。**查不全就说查不全**——漏写的语义依赖、排除范围外的变化、运行环境改变仍需人核对。

需要在阶段之间留对照点时可以记快照：只记版本元数据和路径关系，不复制全文；写进明确授权的位置。比较时**必须报告 added / modified / removed 和受影响条目**。**不要跨工作树复用快照**——分支或提交变了要重新记录。**快照不是阅读记录，也不是授权证据。** 变化本身不是错误，是要处理的数据。**敏感数据不写进文档或索引。**

**盘点边界。** 排除版本库、依赖、构建产物、已安装 skill、潜在密钥文件；只声称遵循**实际应用**的过滤规则，不假称解析了未读取的忽略文件。**因大小、格式或访问限制未完整读取的文件，记录为未覆盖**——不要用排除它们来提高覆盖率：**范围内但跳过的文件仍属于分母**。符号链接、子模块和其他排除项明确披露，需要时另行纳入子范围。普通 Markdown 与文档目录可以不计入**代码**阅读分母，但这不免除阅读相关需求文档的责任。**文件名过滤不是全面脱敏**，实际范围与资源权限要显式说明。

## 2. 讨论与确认

```text
[用户目标 + 当前规格 + 代码事实]
                 |
                 v
[查证事实，找缺口/矛盾/隐含假设]
                 |
                 +--没有重要歧义--> [说明依据，继续已授权工作]
                 |
                 +--存在重要歧义--> [具体场景 + 后果 + 推荐及代价]
                                               |
                                               v
                                       [共同推演；每个明确决定即时保存]
                                               |
                                               +--仍有缺口--> [继续相关讨论]
                                               |
                                               v
                                       [主题收敛，整理三层设计/差异]
                                               |
                                               v
                                       [实现 + 验证 + 更新文档]
```

这不是不可返回的阶段门，也不强迫所有任务问答。契约清楚的修复与等价重构直接执行。

**方案认可 ≠ 实施授权。** 同时读取原始任务、已确认决定和当前规格，区分三个问题：业务/设计是否确认；本次任务是否要求实施；是否还缺真实环境或工具权限。

| 已有事实 | 下一步 |
|---|---|
| 原请求“实现/修复/做完 X”，随后同意 X 的具体方案 | 同一范围的实施意图持续有效；实现、集成、测试、核对，不再问“要不要实现 X” |
| 用户明确“只讨论/只写文档/先别改代码” | 只保存设计，**不动业务代码**；不能把同意方案解读为实施授权 |
| 已确认行为在代码里缺失，修复在当前实施范围内 | 缺失是执行任务，不是新业务决策；直接补齐 |
| 文档仍 `observed`，但真实历史批准已覆盖同一含义与修订 | 查证后补确认来源及状态；这是维护记录，不把字段填写变成新审批 |
| 只有代码现状、搜索或测试通过，没有真实批准 | 仍是 `observed`；不得批量转 `accepted`。确需采纳时围绕实际行为提一次具体问题，不让人批准状态名 |
| 实施中出现新的外部行为、权限、持久化语义、不可逆操作 | 只就新增差异说明场景、影响及推荐；只暂停受影响单元 |
| 环境缺失、权限不足或接口缺失 | 先调查；已授权范围内可补的接线继续做。只有新契约或无法自行解决的外部条件才升级 |

真实批准可来自原任务、当前对话或仓库记录，不要求特殊口令。不明确的“好”只能绑定紧邻、清楚展示的范围。**确认记录不是 AI 给自己授权；测试结果永远不授权需求。** 权限、预算和用户停止指令继续有效。

**AI 主动调查**：目标与边界、场景与失败（非法输入、部分成功、超时、断连、依赖失败、重复请求）、生命周期（谁改状态、合法与非法转换、终态、重试、取消、恢复）、数据（来源、存储、何时可见、归属、保留清理）、协作与约束（事务/并发/兼容性/预算矛盾）。这是分析检查单，不是交给人的长问卷；不适用项需有依据。已确认文档存在矛盾必须指出。允许质疑，不允许自行重写正确行为、放宽测试或声称已获批准。

**记录决定、整理正文、合入现行规格是三个不同动作。** 本轮出现明确批准、撤回、否决、延期或范围变更，在本轮结束前小范围写入已有 `changes/` 提案或功能草稿；不等全部讨论完，也不等用户催。解释性对话无新决定时不制造写入。记录“具体场景、决定、适用边界、理由、确认来源、是否授权实施、尚未决定什么”。含糊的“好/继续”只在紧邻、无歧义的已呈现范围内解释。保存后给一句回执写明实际文件与关键边界；未写入不能说“已记录”。

**怎么解释**：按“何时发生 → 本项目上下文 → 想得到的结果 → 推荐如何实现 → 代价/边界 → 真正需要人决定什么”的顺序。术语在含义之后命名。不先问“要不要幂等键”，先说清“超时重试可能多建任务，建议同一提交用固定标识复用原任务”。一次优先聚焦同一主题最影响正确性的少数问题；给建议，不预设用户同意；不反复询问已在规格或对话明确的信息。事实由 AI 调查，重要行为和取舍交使用者，局部实现自主。**不要把一般架构偏好写成必然真理**（例如“业务规则绝不能在 SQL”不是本 skill 的规则）；有取舍就说明代价，让别人裁决。

编号是机器定位手段，不是用户界面。讨论与报告用领域/功能/模块/行为的自然名称。稳定 ID（`Doc-ID`、R/C/D/E）不删除、不重排；新正文用自然标题加紧随其后的隐藏标记：

```markdown
### 请求超时后再次提交
<!-- ddd:item R-IMPORT-003 -->
同一次提交带原请求标识重试，复用已有任务，不创建重复导入。
```

改可见标题会改变 Markdown 自动锚点：先查实际入链，保留可用旧锚点或修复入链，再核对导航；不能只批量正则去编号。

**交付报告结构**：总体可用性结论 → 按自然名称列已完成的用户行为与实际验证 → 未完成行为及影响 → 下一步（直接继续，或唯一需要人决定的问题）。命令、路径、编号、版本指纹放技术附录。没有用户决策就明确“本轮没有新增决策需要确认”。不用“补了 N 条证据”充当功能结果；尚缺运行路径时第一句就说尚不能端到端使用；测试计数说明必测场景的实际运行范围，不只给总数。

**把三类东西分开**：**必须遵守**（已确认契约、不变量）、**可以自主**（不影响契约的私有拆分、局部命名）、**未知/待验证**（需调查或人裁决）。把所有私有函数都列成决策点不是更严格，而是淹没真正重要的选择。复杂算法写清前后置条件与不变量；普通样板逻辑不用伪代码复述。

需要**追踪**的待决项才用 `D-<主题>-<编号>` 记录：场景、问题、真实选项、推荐理由、代价、适用边界、影响范围、确认来源、是否授权实施、剩余未决。**保留稳定的 `D-` 编号，不重排、不复用**；**撤回决策时标记为撤回，并保留原结论和撤回理由；如有替代决策，记录其内容及替代关系**。**常规选择不必套这十余项**，写清决定与理由即可。**高风险决策要明确答案；已预先授权的范围不反复请示。** 确无可行备选时说明约束，不伪造两套方案。

只有**重大且难以逆转、没有背景会令人困惑、存在真实取舍**的决策才值得单独 ADR。最小 ADR：背景、决定、理由、代价、替代方案、状态与来源；项目已有 ADR 格式优先。术语表仅在确有歧义时添加。

## 3. 设计：三层与 ASCII 图

**文档是讨论结论的工作界面，不是停止思考的理由。** 写下已有的结论，也写下还没想清的地方；示例属于假设场景，不自动构成项目要求。

**模块划分先于实现。** 新增重要功能、拆模块或调整架构时，先读项目概览、领域导航与相关契约，用一个正常场景和一个实际失败场景推演，记录：

| 决定 | 完成标准 |
|---|---|
| 职责与划分理由 | 每个模块拥有明确能力；说明哪些规则共同变化、哪些变化应保持局部 |
| 状态与写入权限 | 每项关键状态有负责模块；调用方通过契约修改，不绕过所有者 |
| 不变量与一致性 | 写清必须共同成立的规则；需要原子修改跨越候选边界时重新审视划分 |
| 公开入口 | 调用方只需了解操作、结果、前提与失败语义；内部类型不泄漏 |
| 依赖方向 | 标明允许依赖、调用契约和禁止的私有访问；与现有依赖核对 |
| 变更隔离 | 用一次可能的规则或存储变化说明哪些模块应受影响及理由 |

领域目录是责任分区，限界上下文是术语与模型保持一致的范围，实现模块拥有接口和实现；三者不机械等同。按业务决定、状态与变化原因组织，文件大小和共享次数只作线索。模块通过少量公开入口隐藏完整规则；将有意义的业务判断与外部 I/O 分开。简单 CRUD 保持简单，不预设微服务、事件总线或统一四层。允许依赖由项目现有 lint、模块导出或架构测试落实；检查真实 imports、循环依赖与共享可变状态，无工具时定向人工核对并说明覆盖限制。

**图的用法**：流程/数据/状态三类图之外，**同一时刻的多参与者交互可用 ASCII 时序图**；多个生命周期对象时**主图展示主要对象、子图分别说明其他对象并明确关系**。**图不是正确性证明**——标识保存与冲突裁决仍要在对应详细设计里核对。

**三层必须分清楚：**
| 层次 | 回答的问题 | 不应变成 |
|---|---|---|
| 需求说明 | 谁在什么前提下需要什么结果，失败/边界行为，怎样验收 | 一句愿望，或夹带未讨论的技术方案 |
| 概要设计 | 模块责任、端到端协作、数据流与状态归属，关键取舍 | 技术栈/目录清单 |
| 详细设计 | 接口和数据契约、合法状态转换、关键处理步骤、不变量、异常与恢复 | 只有抽象原则，或逐函数复制实现 |

feature/module 保留三个 H2 阅读块，内部小节按适用性裁剪。定稿阅读顺序：摘要 → 需求 → 概要 → 详细 → 实现与实际验证。三层是当前规格的阅读结构，不是每次改动的重复作业：修复已有明确契约或等价重构时回读原图和约束，不重画未变化图。**这不省略本次验收、适用失败/边界测试、实际接线与版本核对。**

**三种图，各回答一个问题：**
| 图 | 位置 | 节点和箭头的含义 |
|---|---|---|
| flow 处理流程 | 概要 | 节点是处理步骤，箭头标判断/结果分支 |
| data 数据流 | 概要 | 节点是参与者、处理器、存储，箭头标数据内容/变化 |
| state 状态转换 | 详细 | 节点是业务对象/任务状态，箭头标触发事件、守卫条件 |

状态图不是文档的 `observed/proposed/accepted` 状态机；不把流程步骤、数据库记录和业务状态混成一套节点。用 Markdown `text`（或 `ascii`）围栏，连线用 `- | + > < v ^`，节点可写中文，不依赖渲染器才能读懂。

```text
[输入] --合法--> [处理] --成功--> [输出]
   |
   +--非法--> [拒绝并说明原因]
```

图后必须解释前提、分支条件、数据归属、可见性与关键副作用。大图按子流程分解并命名引用。正文中的接口、状态、数据名和测试场景使用相同术语。现状图只画有依据的机制；没查清的转换记录调查缺口，不能把空白随便连到失败或成功。

**沿图走查**：至少选一个正常场景和一个实际相关的失败/边界场景，适用时再走重复、并发、取消或恢复路径。逐步问：读/写什么，谁改变状态，何时可见，异常由谁接手，用户看到什么，测试如何观察。孤立状态、无主数据、无来源输入、未定义异常、跨图矛盾必须说明；能自行查明的查明，需要业务决定的讨论，**不为通过检查虚构重试、事务或性能保证**。

新建或本次明确完成结构升级的 feature/module 在头部加 `Design-Format: layered-v1`。三层以 H2 标题识别（中文“需求说明/概要设计/详细设计”等，或英文 `Requirements`/`High-level design`/`Detailed design`，允许数字前缀）；其他语言的既有标题不必改名，在相应 H2 后紧接 `<!-- ddd:section requirements|overview|detail -->`。需求层包含有内容的“验收”子标题或 `<!-- ddd:acceptance -->`。每种主图一个标记直接接闭合围栏（flow/data 在概要层，state 在详细层）。不适用与未查清必须分开：`not-applicable: <理由>` 不接受只写“无/不适用”，`pending: <缺什么>` 在 `accepted` 或定稿核对中不能隐藏。共享图用 `ref: <受管文档路径>`，被引用文件必须存在、含对应标记，禁止循环。

**实施前评审**：讨论中对每个重要结论做局部冲突检查；进入实施前按风险做设计评审，修正后定向复核。普通小改可一次自审；高风险（权限、持久化、并发、跨模块协议、不可逆操作）优先用独立只读评审者。宿主无子 agent 时单独自审并披露局限，**不能虚构调用记录**。评审者不改文件；主 agent 是唯一整合写入者，先查证再决定采纳或给出理由。每项意见给位置、可复现场景或矛盾依据、影响与建议，并分类：已证实缺陷/待调查/不成立/可选改进。结束条件是本次已知阻塞项全部解决、范围缩小或明确接受可界定风险。

## 4. 实施

```text
[已确认目标 + 原任务要求实施]
                  |
                  v
[列出当前范围所有重要行为和验收场景]
                  |
                  v
[开发] --> [接入实际入口] --> [真实验证] --> [双向核对]
   ^                |              |               |
   +------范围内缺失/偏差-----------+---------------+
                  |
                  +--新增设计选择--> [只讨论新增差异]
                  +--外部条件受阻--> [保存阻塞；继续无关单元]
                  +--全部满足------> [说明用户能做什么及验证边界]
```

每次阶段结束后执行下一项已授权工作，而不是用“下一步可以……”替代执行。到达真实阻塞、权限/预算边界或会话容量边界时，保存实际成果、下一项及原因，**不声称后台继续**。

**以最小可用行为切片，而非文件或编号清单。** 先定义一条用户可观察路径（例如“提交消息后被正式派发”，不是“增加两个端口方法”），再分开发、测试与集成责任。对每条交付单元在已有变更提案中保留：自然名称、原确认与实施授权来源、目标规格修订、所覆盖行为、允许修改范围、不可改变约束、入口和调用链、验收方法、依赖、执行者/集成人、当前状态和实际阻塞。小修用几行即可；跨模块、正式入口接线或多 agent 分工时必须用可检查交付包。

编码前按项目概览 → 所属领域 → 本次功能/模块 → 必要上下游读取，核对职责、公开入口、状态写入权限、不变量与允许依赖。完成本次 diff 后按 [FORMATS.md](FORMATS.md) 的更新触发逐项判断：外部行为、所有权、入口或依赖改变则更新相应主契约；私有重构通常只改代码/测试和必要路径。边界偏差在本范围内修复；新重要取舍只讨论新增部分。

**每个单元完成需同时满足**：范围内无遗漏、入口到结果链路可达、必测实际运行、未引入未批准行为、当前规格与最终集成代码匹配。子 agent 的 passed 只是报告；集成人核对 diff、实际产物及最终装配，合并后执行必要集成/验收，**不把分支绿色直接相加**。未接通/未验证标 partial 或 blocked；仅已批准延期才排除。

**人工改过代码之后**：先比较文档、工作树和变更基线，**不先假定任一方永远正确**。

| 发现 | 处理 |
|---|---|
| 代码偏离已确认要求 | 按要求修代码并补回归验证；**不修改要求迁就 BUG**。恢复所属模块的修改权与去重行为，**加入能在错误实现上失败的回归**；完成条件是实现重新满足现行契约 |
| 等价重构或定位变化 | 按请求处理，更新定位与受影响证据，不重审无关设计 |
| 人已直接编码某已批准行为/方案 | 记录真实批准范围，补当前文档并核对，标明代码优先来源 |
| 代码引入新的未确认重要选择 | 记录差异与提案，**不自动补成 `accepted`** |
| 旧文档与代码矛盾且缺权威来源 | 分开记录两者、影响和未知；需决定的部分提交人确认 |
| 代码似有缺陷但需求不明 | 区分静态事实与疑似问题；建立隔离的现状测试，不把它当正确性验收 |

**"直接修改代码"授权的是工作方式，不是无限授权新设计。** 紧急修复可按明确授权的有限目标先做，但要记录尚未确认的差异和回滚边界，不能据此标记整个契约获批。

复杂交付做**两遍核对**，都要真做：**覆盖**——以本次真实比较基线只选当前范围，逐个单元核对是否覆盖获批行为；仅实施一部分时用 selectedItems + scopeSource 记录原授权小范围，deferred 要有原因和真实批准。**完成**——先真正完成实现/测试/集成再判 done；仍缺失、受阻、基于旧版本或跳过必测的单元不算完成。状态 `queued/implementing/integrating/verifying/done/blocked` 是机器字段，用户报告用“待执行/开发中/正在接通/验证中/已验证/受阻”。

**严格交付核对**是这套核对里最严的一档：严格核对时，**检查者应把**受影响文档未确认、未完整实现或未通过验证的状态**判为不通过**。它是**可选门禁**——需要时用于正式交付，不妨碍只做逆向记录或渐进接管。覆盖核对只能防止**声明范围**里遗漏单元，**不能证明已声明了全部业务需求**；这类核对不执行代码、不启动 agent、不认证授权，实际调用链与验收仍须由执行者与集成人核对。

## 5. 验证

**先定义必测，再谈执行。** 在功能/模块规格的验收部分把五件事说清：**场景**（什么时候发生）、**真实入口**（从哪个入口操作）、**预期结果**（期待看到什么）、**方法**（用什么检查）、**环境**（前提条件）；并写明异常时什么不能发生。随后在 `docs/changes/` 放一份短执行计划（模板见 [FORMATS.md 第 5.6 节](FORMATS.md#56-verification-plan验收执行计划)），引用规格身份与场景，不另抄业务需求。计划默认绑定文档全部 R/C；只做一部分要有 selectedItems 和真实 scopeSource，不能为了变绿缩小已授权任务。所有列出的检查均为必需检查；可选测试的跳过必须明确命名及理由，**不能把必测放进可选**。

| 三层内容 | 应证明什么 | 不能代替它的东西 |
|---|---|---|
| 需求说明 | 使用者可观察到的成功、失败、边界行为 | 方法存在、日志有字、作者说 done |
| 概要设计 | 实际装配、调用者、持久化与消费者接通 | 仅 mock 或直接调用组件 |
| 详细设计 | 接口、算法、不变量、状态和数据约束 | 覆盖率数字本身 |

**三个动作：预览、执行、复核。** 阶段划分是约束，实现方式不是。

1. **预览（只读）**：不创建运行目录、不运行项目代码。产出一份可核对的执行计划，并给出该计划的内容指纹。审阅者要能看清：将要运行哪些检查、用什么命令、绑定哪些输入。
2. **执行**：只有在核对计划、命令、环境和已有授权之后，并且**实际指纹与预览一致**时才执行。指纹不一致就停下，不要“反正差不多”地跑下去。
3. **复核（只读）**：只读本次实际产物，核对声明与结果是否一致；不自动编辑文档。

计划语法错误、指纹不匹配，或用户声明仅设计/暂停时**不执行**。**建立验证约定不等于获得运行项目测试的授权**；命令会触及新权限、付费服务、生产资源或破坏性操作时，只就新增边界确认。预览指纹是防止执行另一份计划，不是让用户手工批准哈希。

**验证过程必须满足的性质**：先固定规格、计划、代码快照、测试/配置输入、项目规则及运行工具的内容指纹；开始前与结束后再次核对，变化不自动重贴哈希。按计划顺序运行，依赖只允许指向前面的检查；失败依赖阻塞下游但不阻止无关检查。同一工作树同一时间只允许一个验证实例；**并发改动不得混成同一验证快照**。以参数数组启动真实子进程，不隐式添加 shell；记录命令、工作目录、时间、退出码/信号、超时/中断和有限长度的 stdout/stderr。测试名前后必须精确匹配必测用例，**不能用不相关的通过用例代替**。

| 情况 | 结论 |
|---|---|
| 必需的命名用例都执行通过；无失败；当前版本匹配 | 本次声明范围已验证 |
| 必测 missing / SKIP / TODO、零实际执行、任何实际失败、非零退出 | 失败，不能以总命令返回 ok 覆盖 |
| 缺必需环境变量、输入或可执行工具，或依赖失败 | 受阻；记录缺失名称，**不记录密钥值** |
| 超时、中断、输出超限或无法解析报告 | 不通过；保留实际结果，不猜计数 |
| 执行中或执行后代码、规格、计划、输入改变 | 过期；查差异后重跑相关检查 |
| manual 检查 | 待人工验收；不伪造人类签字 |

命令型检查（编译、类型、静态检查）使用退出码，**没有伪造的测试数量**，只允许 static/component 层次，不可覆盖 integration/acceptance。

**证据绑定与失效**：证据绑定规格、代码、输入、工具与输出五个身份。规格、代码或输入任一改变，旧证据即失效，须重新核对或重跑——**不把新指纹自动贴到旧 passed 记录**。仅复用旧结果时必须另记录本次真实核对的范围、方法和理由，不能冒称重跑。需要人工的交付继续清楚标识，不能宣称所有机器门禁已完成。

**双向核对**（两个方向都要做，不是二选一）：

- **规格 → 代码**：先列本次重要要求，再读实现与测试，把每条分类为**已满足 / 缺失 / 偏离 / 无法验证**。
- **代码 → 授权**：以**行为与范围变化**为单位核对，不逐行要求重新批准。授权依据包括用户现有指令及其**合理包含**的实现工作；超出该范围的顺手新增要单独指出。

实施前先从需求制定关键验收，**不能只按既有实现写断言**（那是拿代码证明代码）；高风险项按成本做反例或故障验证。新代码不符合要求时优先修代码；要改要求就开新提案。文档记录明显有错时，修正观察并保留理由，**不把错误描述强加给代码**。

同一规格/代码版本下仍留有 failed 记录时，**不自动采用"最后一次通过"**。必须在原记录中保留问题及其真实处理/复核来源后更新结论，或在新版本下重新验证；**未解决的失败必须保持可见**，不得靠删除记录掩盖。绑定统计按 `Covers` 涉及的目标文档计数，不是测试条数或正确率；"当前"只说明版本相符。

**采证**：只在新目录写入产物，不覆盖历史运行或项目文档；失败和成功分别保留，不提供“不断重试直到绿并删除前次失败”。强杀或断电可能只留下部分产物，不能当作有效证据。复核时直接从通过当前版本核验的记录判定场景、方法、验证层与代码基线，不要求再抄完整证据副本；提供旧字段时仍检查矛盾。

**安全边界**：验证流程不是沙箱或签名服务，不能限制被执行脚本的文件、网络或数据库权限。执行前读真实脚本、确认资源和运行目录；测试任务不自动授权安装依赖、迁移数据库、启动生产服务或删除卷。默认只继承基本系统环境，其他环境变量须显式列名，不记录值。本地哈希只检测意外变化，**不是防恶意篡改**；关键交付应由受保护 CI 或独立环境重跑。**实际断言通过也不能证明需求完整或测试有效**；人的批准不能从测试结果推导。**含秘密的环境值不存哈希**（避免对短值离线猜测）；**数据库内容、远程服务状态这类外部事实不能靠本地哈希验证**，须用隔离环境标识和实际检查控制。

**资源清理的所有权边界**：清理资源只能删除**能证明由本次任务创建且已获准删除**的资源；匿名 Docker 卷不等于临时数据，也不等于可删除数据，不能从卷名或匿名状态推断所有权，**禁止把全局 `prune` 当常规测试修复**。空间不足时先限制日志或构建开销；需处理其他数据时单独说明并确认，并记录资源标识、生命周期和清理结果。

**不得制造绿色**：不通过删除必测、弱化断言、缩小未获准范围、改规格或刷新旧哈希来变绿。组件存在、退出码 0、SKIP/TODO、零执行、未知解析、空日志都不证明实际场景通过。不得自己改运行记录或重算校验伪装重测。校验计划只确认声明范围有检查，不会发现所有遗漏业务场景；执行前从原始目标复核范围与断言，实施后双向核对，**不得以一个 happy path 覆盖 R/C 就声称穷尽**。

**行为评估的达标条件**：按人工评分标准判断结论、漏项和误报，**不以"发现固定数量的问题"作为达标条件**。评测跑一例是一次完整人工会话；具体场景与评分标准见[真实宿主评测起步集](examples/evaluation-cases.md)。

## 6. 多 agent 分工（可选）

先检查当前宿主实际可用的委托、模型选择、并行、权限和上下文能力。没有子 agent 时单 agent 顺序执行同样边界，明确实际模式；**不能假称已派发独立评审或换用了便宜模型**。

```text
[使用者] <--> [主 agent：规格、授权、验收责任]
                         |
             +-----------+-------------+
             v           v             v
          [开发]      [测试]       [只读评审]
             +-----------+-------------+
                         v
                [主 agent：集成核对]
```

**文档只有一个主写入者**，可以是强设计主持者；协调者只保存明确的工作状态，不同时改契约。开发 worker 只改分配路径，提交建议而不私自修订需求；评审 worker 默认只读。设计主持者失效时先保存版本化移交，再更换写入者。技术验收可委托，最终范围声明与对用户责任仍由指定主 agent 负责；不要让廉价协调者不查证就复述“通过”。子 agent 不能扩大用户权限或批准业务变化。

**委托边界**：每次派发复用已有提案内的交付单元，传递最小充分上下文——自然名称和用户结果；准确规格修订/条目及关键原文入口；真实实施授权；允许写入路径与禁止修改；状态、接口及不变量；前置依赖；入口接线责任；测试与环境；交付物和停止条件；预算/重试边界。不要只发“实现 C2”，也不要无差别复制整库历史。worker 开始前回读当前原文并对比指纹，发现规格变更返回主持者，不能用老快照执行。返回内容：实际 diff、自然名称下实现了什么、还缺什么、实际命令与非空产物、必测 executed/skipped/failed、规格和代码身份、受阻原因、真实资源消耗——**不能只返回“done”**。

**并行和成本纪律**：只并行无文件冲突且接口边界稳定的工作。同一路径多个写入者必须分离工作树并指定合并者；**创建工作树同样需要权限**；无法隔离则排队。外部服务、数据库和 Docker 资源同样需要独立命名、所有权和清理预算。**对子 agent 默认只授予相应的写路径**，不授予 grader、验收门禁、生产秘密或全局清理能力。**能由确定性脚本完成的检查不另开模型。** 不承诺多 agent 必然省钱——主 agent 思考、worker 上下文、复核、失败重试、工具与环境成本都计入总成本；高风险复杂实现可直接用强模型。**不硬编码价格、模型排名，也不虚构支持的子 agent API**；用特定宿主或模型的最新能力前先查其官方文档。未给额度不编造美元上限。默认单层委托、最少必要 worker；**宿主支持再委托时必须显式设置深度与预算，默认不递归**；同一失败不得无界重试。宿主不提供账单时写“未测量”，不报告“节省了 X%”。

**成本对照指标**：端到端实际费用、完成时长、**用户重复确认次数、返工次数、真正完成的行为数量**。不能只比 token 单价——单价低但返工多，总成本更高。

**两种委托形态**：**单层委托**（默认，最少必要 worker）与**常驻协调者 + 按需委托**——后者由协调者独占对话与任务调度，只在需要设计判断时委托给强模型主持者，理由是**不让昂贵模型持续读取所有日志**；结果经版本化任务约定交指定集成人核对，再由协调者报告。两种形态都不改变"单一文档写入者"与最终集成责任。

## 7. 不可缩减的边界

六条边界由 [SKILL.md](SKILL.md)「不可缩减的边界」统一维护，不在本页复制第二套。资源清理的所有权边界见第 5 节「安全边界」。

## 失去的机械保证

以下能力原先由配套程序提供，现已随脚本移除。现在全部靠人和约定：

| 原能力 | 现在的状况 |
|---|---|
| 三层结构、占位、图容器、引用、版本绑定的自动核对 | 无。对着模板人工逐项看，漏项不会被发现；也没有机器结论可引用 |
| 「预览指纹 → 实际执行」的绑定 | 原来由程序强制，现在靠人。**比错不会报错** |
| 运行收据的产出与自校验 | 无。`run.json#sha256` 只是你自己写下的字符串，没有东西验证它 |
| 字段、状态、必测缺失、格式漂移的自动发现 | 无。链接失效、格式漂移、必测缺失不再自动暴露 |
| 交付单元覆盖/完成的机器核对 | 无。R/C 要自己展开列全，缺失、受阻、旧版本或跳过必测的单元不再被拦截 |
| 全文检索与依赖图双向遍历 | 无。手工顺着 `Depends on` 读，慢且不再可重复 |
| 文档身份与代码基线的自动绑定、快照比较 | 无。手工核对版本、手工比较 |

**本页因此只是方法，不是工具说明。** 判定表、三层证据要求和边界仍然逐条有效，只是不再有程序兜底；没有任何机制能发现“声称做过、实际没做”。代码侧的事实不受影响——那部分本来就该由代码图谱工具负责，不是本 skill 的职责。
