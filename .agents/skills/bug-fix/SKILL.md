# 问题修复

起点是故障，但还说不清为什么。

**铁律：没有红灯循环，就不进入假设阶段。** 红灯循环 = 一个你已经跑过一次的命令，它能对**这个** bug 判红。

**记号**：`/x` 是只能你亲手敲的 skill；不带斜杠的 `x` 模型会自己调用。

**先读原文。** 调用 Skill 工具加载 `diagnosing-bugs`，按它的六个阶段执行。下面只是路标，判据以它为准。

## 路线

1. **建红灯循环**（Phase 1，这一步占大头）—— 依次试：失败测试 / curl / CLI 快照 / 无头浏览器 / 重放 trace / 一次性 harness / fuzz / bisect / 差分 / HITL 脚本。
   *完成判据*：一个命令，已跑过并展示输出，能红、确定性、秒级、可无人值守。

2. **复现 + 最小化** —— 逐个删输入、调用方、配置、数据，每删一次重跑。
   *完成判据*：每个剩余元素都承载，删任何一个就变绿。

3. **假设** —— 先写 3–5 个可证伪假设并排序，给用户看再验。
   *完成判据*：每个假设都能说出「若 X 是原因，则改 Y 会让它消失」。

4. **仪器** —— 一次只改一个变量；每条日志带统一前缀，收尾时一条 grep 清干净。

5. **修复 + 回归测试** —— 先写会失败的测试，再修，再复跑第 1 步的原场景。
   *完成判据*：原场景不再复现，回归测试通过，仪器已清空。

6. **收** —— 让你运行 `/retro`，问一句什么能预防它。

## 岔路

- **找不到合适的测试缝**：这本身是结论，不是失败。转 `/improve-codebase-architecture`，别在浅缝上写一个假安心的测试。
- **外来报来的 bug**：先运行 `/triage` 归位（分类、验证、写成 agent-ready），再回到第 1 步。
- **性能回归**：日志通常没用。先建立基线测量，再二分。
- **还没复现就想重构**：先回到第 1 步。重构会换一个地方继续猜。
